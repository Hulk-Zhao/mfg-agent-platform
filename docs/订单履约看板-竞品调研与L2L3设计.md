# 订单履约看板：竞品调研与 L2/L3 下钻设计

> 角色：资深产品经理 · 面向对象：产品/研发/供应链/销售运营/管理层
> 目标：以交付类核心 KPI 为锚，把仅有 L1 静态演示的「订单履约看板」升级为 **L1 KPI → L2 维度分解 → L3 单实体明细** 的可下钻三级看板，并与平台既有「协同问数」打通——任一指标/明细都可一键带上下文跳到问数（chat）继续追问。

---

## 一、结论先行（TL;DR）

1. **订单履约是"结果指标"看板，与制造/品质看板（过程指标）互补**：订单履约看整体"是否按时、按量交付到客户"，制造看板看"产线过程是否健康"。两者共用同一套下钻机件，形成"结果异常 → 过程归因"的闭环。
2. **对标锚点是 OTIF**：国际主流 OMS/SCM 看板普遍以 **OTIF（On-Time In-Full，准时足额率）** 为核心北极星指标，OTD（准时交付率）作为其放宽口径的"准时侧"分解，Fill Rate（订单满足率）、Late Orders（延期订单）为伴随指标。本看板直接采用这套行业通用口径。
3. **下钻范式照搬成熟 BI**：帆软 FineBI「图表内钻取」、观远 BI「多层/自由下钻（L1→L2→L3 + 面包屑）」已证明"三级下钻 + 逐级返回"是最易被业务接受的探索路径；本看板严格复用该形态，并额外叠加**跨屏协同问数**（BI 厂商需付费/定制才有的 NL2SQL 追问能力，本平台为原生能力）。
4. **复用优先、零重复造轮子**：L2/L3 完全复用平台既有 `build_drill` 聚合引擎（仅扩展 `customer` 实体类型 + 中文表头），前端复用 `BOARD_CFG`+`boardDrill` 下钻状态机，制造看板与订单看板**共用同一套约 300 行下钻代码**。
5. **治理一致、降级不崩**：全部只读 SQL、命名绑定参数、异常兜底记 `degraded_reason`、绝不抛 500；前端"真实优先 + 演示降级"双路，断网/后端异常时自动回落离线快照并打 `demo` 徽标。

## 二、竞品调研

调研视角：以"**订单履约类看板的指标口径 + 下钻交互范式**"为筛选标准，覆盖国产 BI、国际 BI、以及 ERP/SCM 厂商的交付类看板。

### 2.1 通用 BI 厂商（下钻交互范式来源）

- **帆软 FineBI**：图表支持**内钻取（drill-down）**——点击某维度点即切换为该点的明细/下级维度，配合组件内"返回"按钮；支持联动与跳转传参（[FineBI 钻取](https://help.fanruan.com/finebi/doc-view-1061.html)）。是国产 BI 中"点击即下钻"体验最成熟的范式。
- **观远 BI**：明确提供**多层下钻 + 自由下钻**（用户可自行定义任意层级路径），并有**面包屑**回溯，是企业内"从大盘到明细"探索的标准做法（[观远 BI](https://www.guandata.com/)）。
- **Power BI / Tableau**：通过 Hierarchy 与 Drill mode、Set Actions 实现逐层下钻，参数化跳转可传上下文——是国际 BI 的通用能力，但**NL 追问（自然语言问数）需额外配置 Copilot/Q&A 且受语义模型约束**。

**对本看板的启示**：L1→L2→L3 的层级结构 + 面包屑逐级返回 + 每级保留口径说明，是"零培训成本"的交互共识。

### 2.2 ERP / SCM 厂商（指标口径来源）

- **金蝶云星空 / 云·订单承诺智能体**：以"订单承诺"为主线，提供**逐单追踪 + 逾期归因**（交期承诺 → 执行跟踪 → 逾期预警与原因）。
- **用友 BIP / U8+ 供应链**：提供订单执行全流程看板（下单→排产→采购→生产→发货），强调**交期达成率**与**齐套率**对交付的保障关系。
- **SAP IBP / OMS、Oracle SCM**：行业标准交付 KPI 为 **OTIF、OTD、Order Fill Rate、Backlog/Aged Orders**。

**对本看板的启示**：指标口径应与行业对齐（OTD/OTIF/延期率/齐套率），且必须能**从结果指标下钻到"是哪张单、卡在哪个环节、缺什么料"**——这正是 L3 要承载的价值。

### 2.3 交付类核心 KPI 定义（行业通用口径）

| 指标 | 英文 | 定义（行业通用） | 极性 |
|---|---|---|---|
| OTD 准时交付率 | On-Time Delivery | 实际发货日 ≤ 客户要求交付日 的订单数 ÷ 订单总数 | 越高越好 |
| OTIF 准时足额率 | On-Time In-Full | 同时满足"准时"且"足额（齐套发齐）"的订单数 ÷ 订单总数 | 越高越好（更严格） |
| 延期订单率 | Late Orders Rate | 延期天数 > 0 的订单数 ÷ 订单总数 | 越低越好 |
| 齐套率 | Kit / Material Readiness | 已齐套料数 ÷ 应齐套料数 | 越高越好 |
| 订单满足率 | Fill Rate | 已发数量 ÷ 订单需求数量 | 越高越好 |

> 本看板取 **OTD / OTIF / 延期订单率 / 齐套率** 四个 KPI：前者是"客户视角的结果"，齐套率是"内部可干预的抓手"，形成"结果—归因"配对。

### 2.4 协同问数：BI 能力的"最后一公里"

- 通用 BI 的自然语言问数（NL2SQL / Q&A）通常：**需单独建设语义模型、需付费高级许可、且只能在自己数据域内提问**。
- 本平台的**协同问数**是原生能力：看板任一 KPI/明细行都可携带上下文（指标名/客户/型号/订单号）一键跳转 chat，由统一 Agent 编排链路继续做**跨域**追问（如"OTD 低的这批订单，是不是某条产线稼动率低导致的？"——直接打通到制造看板数据）。
- 这是**看板（看清）→ 问数（问因）→ 协同（跨域归因）**的闭环，也是相对通用 BI 的差异化。

## 四、指标口径与达标判定

### 4.1 口径即代码

全部口径落在 `dashboard.py` 的常量 SQL 中（**绝不拼接用户输入**，取值一律命名绑定参数），保证"看板显示的口径 = 代码里的口径 = 问数回答的口径"三者一致：

- `otd`   ：`SUM(on_time) / COUNT(*)`，按 `customer, customer_level` 分组，L2 维度 = **客户 · 等级**
- `otif`  ：`SUM(CASE WHEN on_time=1 AND in_full=1 THEN 1 ELSE 0 END) / COUNT(*)`，同 L2 维度
- `delay_rate`：`SUM(CASE WHEN delay_days>0 THEN 1 ELSE 0 END) / COUNT(*)`，同 L2 维度
- `kit_rate`：`SUM(kit_done_qty) / SUM(kit_total_qty)`，按 `product_model` 分组，L2 维度 = **型号**

窗口：订单按 **客户要求交付日 `due_date`** 归入演示窗口（`2026-10-08 ~ 2026-10-14`，7 天）。

### 4.2 达标判定（极性自适应）

统一由 `_status(value, target, higher_is_better)` 判定：

- **越高越好**（OTD/OTIF/齐套率）：`value ≥ target` → `ok`；`≥ target×0.9` → `warn`；否则 `danger`。
- **越低越好**（延期订单率）：`value ≤ target` → `ok`；`≤ target×1.5` → `warn`；否则 `danger`。

目标线：OTD 98%、OTIF 95%、延期订单率 5%、齐套率 95%。TOP5 统一为「最需关注的**最差 5 名**」，方向随极性自动翻转（越高越好取最低 5、越低越好取最高 5）。

## 五、L1 / L2 / L3 三级下钻设计

### 5.1 L1 · 总览（订单履约全景）

- **4 个 KPI 卡**：OTD / OTIF / 延期订单率 / 齐套率 —— 显示当前值、目标值、达标色（ok/warn/danger）、环比目标差值、7 日迷你趋势线（`mfgSpark` 内联 SVG）。
- **4 个 TOP5 排行**：每个 KPI 一张"最需关注的 5 个维度组合"（客户·等级 或 型号），行内显示数值/分子分母/达标色。
- **状态管道**：已下单 → 计划 → 采购 → 生产 → 质检 → 发货，各环节数量 + 其中延期数（一眼看出"订单卡在哪"）。
- **风险订单清单**：`risk_type ≠ 正常` 的订单，按延期天数降序取 8 条，展示订单号/客户/型号/数量/当前环节/风险类型/延期天数/进度/缺料说明/责任人，**每单带「问数」按钮**。
- **口径说明（notes）**：4 条指标口径 + TOP5 规则，随看板内嵌展示，降低口径歧义。

### 5.2 L2 · 维度分解（全量清单）

- 从 L1 任一 KPI 卡点击进入，按该指标的 **L2 维度**（客户·等级 / 型号）**全量列出**所有组合：数值、分子/分母、达标色。
- 支持"问数"（带指标上下文）与"返回 L1"面包屑。
- **实体透传**：每行携带 `entity`（`{customer, level}` 或 `{model}`），为 L3 直下做定位。

### 5.3 L3 · 单实体明细（结果落到单）

- 点击 L2 某行进入，展示该实体在窗口内的：
  - **大字当前值** + 达标色 + 与目标差值；
  - **7 日逐日表**（每日分子/分母/值）；
  - **关联原始记录明细**：订单号/客户/等级/型号/数量/交付日/发货日/延期天数/环节/风险类型/缺料说明（订单表的 11 列出齐），让业务"看到是哪张单、卡在哪、缺什么料"。
- 同样支持"问数"（带上实体上下文，如"客户 华为·S 的 OTD 明细"）与面包屑逐级返回。

### 5.4 面包屑导航

`订单履约看板 › <KPI> › <实体>` 三段式，逐级可点返回；返回上级时保留已选 KPI（不清空上下文）。

## 六、协同问数联动机制

- **联动方式**：看板任意 KPI 卡/L2 行/L3 实体/L1 风险订单行的「问数」按钮 → `sessionStorage.setItem("chat_prefill", q)` → `ctx.navigate("chat")`，chat 页读取预填问题直接发起。
- **上下文粒度**：
  - KPI 卡 → 指标级问法（如"最近7天各客户 OTD 准时交付率如何？最低的是哪个客户？"）
  - 风险订单 → 单级问法（如"订单 SO-2026-10247（华为终端）延期 4 天，卡在质检环节，原因是什么？如何补救？"）
  - L3 实体 → 实体级问法（如"客户 华为·S 的 OTD 明细与延期原因"）
- **跨域归因**：因问数走平台统一 Agent 编排（TwoLevelRouter → 场景 DAG），同一句话可同时命中制造/品质/供应链域，实现"订单结果 → 产线/物料过程"的跨域追问——这是通用 BI 无法提供的闭环。
