✗ 架构层面的真问题

你把平台切成了读路径（业务数据，走 DataSource 契约）和写路径（治理数据，裸 sqlite3）， 两条路径用两套持久化机制。而契约层只覆盖了一半——"契约"这个词在你的架构图里被高估了。 客户做技术尽调，第一个问的就是这个。

怎么改（不必大重构）

核心思路：不要为了 MySQL 重写 1025 行，而是先把"不能换"这件事变成显式的、可检测的，再决定换不换。

第一步 · 止血（半天，必做）

  • 在 WorkflowEngine.__init__ 里加硬校验：db_url 不以 sqlite 开头就抛 NotImplementedError("WorkflowEngine 目前仅支持 SQLite，见 README 生产化清单")。
  • 把 config.py 里的 WORKFLOW_DB 与 DB_URL 解耦——现在默认继承 DB_URL 就是地雷。
  • README 的部署表格里，"中间件栈"一行加一列明确标注：「治理数据仍在 SQLite（单点）」，别让读者以为一键生产。

收益：不会再有客户/同事踩到静默分裂数据的坑。这一步没有风险，立刻做。

第二步 · 抽仓储接口（2-3 天）

在 contracts/ 下加一个 WorkflowRepository 抽象（create_task / get / transition / append_approval / list_pending 五个方法就够）， WorkflowEngine 只依赖它。SqliteWorkflowRepository 把现有 1025 行原样搬进去——逻辑零改动。

这样你立刻获得两个东西：① 单测可以用 :memory: 实现，跑得更快； ② 将来写 SqlAlchemyWorkflowRepository 时，WorkflowEngine 一个字都不用动。

这与你已有的 DataSource / VectorStore / IMGateway 三契约完全同构， 架构叙事也就自洽了：四契约，而不是"三个契约 + 一个特例"。

第三步 · 真正上 MySQL（按需，1-2 天）

只有当客户明确要"多实例 / 高可用"时才做。前提是第二步已完成，否则直接改 workflow.py 是灾难。

顺带把 README 生产化清单里的"会签并发幂等需 DB 级"一起解决——独立签名表 + UNIQUE(task_uid, role_key, actor, verb) 唯一索引，替换掉现在的进程内 RLock。 这两件事天然是一起做的，分开做等于返工。

怎么改

方案 A · 声明式数据范围目录（推荐，与现有范式同构）

你已经有一个极好的模式：权限目录声明在 YAML，构造期自检。把它复制一份给数据可见性即可。

# 提案形态（实际落地见下方说明）
dashboard_scopes:
  manufacturing:
    default: [gm, mfg, eq, eqm, mt, qd, pqe, ie]
    masked:  [hr, fin, proc]        # 可见但脱敏（隐藏成本/客户名）
    denied:  [cs, biz]              # 403
  spc:
    default: [gm, qd, pqe, sqe, qa, pe, te]
    denied:  [hr, finm, fin, cs, biz, procm, whm, wh]

关键收益：这份 YAML 可以反哺前端——/api/v2/agents/configs 已经在返回角色配置了， 加一个 nav_scope 字段，导航收敛（见 P1-1）就是免费的，不用再维护第二份映射。

实际落地形态（与上面提案的差异，以及为什么）

路径：落在 src/mfg_agents/v2/data/data_scope.yaml，与已有的 permissions.yaml / queries.yaml 同目录——治理数据集中一处， 比另开 config/ 更好找。

结构：default / masked / denied 三档简化为 allow_roles + 字段级 mask[]。理由：三档里 masked 到底遮哪几个字段 说不清，而"把人挡在门外"和"进去但看不见客户是谁"是两种完全不同的语义，用两个结构表达比用三个标签清楚。

脱敏键：mask[] 的每条规则声明 path（支持 rankings[key=otd].items[].name 这类维度选择器）+ keep_roles + 替换策略（稳定代号 / 固定文本）。客户代号按字典序分配，同一客户在风险清单与排行里 代号相同——否则两张表一比对就能还原。

没有照抄 nav_scope 反哺前端：前端 NAV_ITEMS[].roles 已按岗位职责写完， 再让后端下发会变成第三份事实源。改为测试交叉校验两份目录的角色集合，不一致就红。

✗ 这次没覆盖到的，别当成已经解决

① 行级范围：现在回答的是"这个岗位能不能看这块数据"，还没回答"能不能看他这条线的"。 数据范围目录需要从角色维度扩到组织维度（dept / line / 本人辖区）， 这才是真实制造企业的诉求。

② 待办中心仍是全局的：HR 隐藏了看板菜单，但"待人工确认 504"仍是全厂计数、 待办列表仍能看到品质 8D 工单。/api/v2/workflow/pending 走的是会签角色过滤 （只过滤"该不该我签"），不是数据范围过滤。这条必须单独排期。

③ 旁路还没堵完：/api/v2/data/describe 会吐出数据源与表结构； Text2SQL 通道能问出"华为终端的 OTD"——它走表级 ACL，但不认这份 data_scope.yaml。 两个通道、两套口径，是目前最不一致的地方。

→ 这一步做完，你的架构故事就闭环了

"一个声明式治理目录，管住三件事：谁能签、谁能看、谁能用哪个屏"—— 这句话比现在的"24 条权限 + 8 个 HITL 槽位"好讲得多，客户也听得懂。

04P0-3　部署分布：两个 compose 是平行线

检查项docker-compose.yml（app）docker-compose.infra.yml后果
是否读 .env无 env_file无只有 yaml 里写了 ${} 的才生效
DB_URL未传—app 永远 SQLite
VECTOR_BACKEND未传—回落默认 chroma，Milvus 白起
REDIS_URL未传—缓存永久降级，限流失效
网络defaultname: mfg_infra容器内解析不到 mysql
模型权重dockerignore 排除 models/—镜像里没有 bge-m3，RAG 无从跑
⚠ 这就导致一个尴尬事实

你的"生产部署"路径实际上只能是：docker compose 起中间件 + 宿主机上 uv 裸跑应用。 这条路能通，但它不是"部署"，是"开发环境"。而 README 的部署表格让人以为有三个形态可选。

怎么改：一个 compose、三个 profile

别维护两份 yaml。合成一份，用 profiles: 区分形态，env_file 统一注入。

services:
  app:
    env_file: .env                  # ← 一行解决 90% 的配置漂移
    networks: [mfg_net]
    depends_on:
      mysql:   { condition: service_healthy, required: false }
      redis:   { condition: service_healthy, required: false }

  mysql:  { profiles: [infra] }        # 不激活就不起
  milvus: { profiles: [infra, rag] }
  redis:  { profiles: [infra] }

networks:
  mfg_net: {}                          # 单一网络，别用两份 yaml 各自的默认网

用法变成：

docker compose up -d                      # 演示：只起 app（SQLite + Chroma）
docker compose --profile infra up -d      # 生产：app + MySQL + Redis
docker compose --profile rag  up -d       # 全栈：再加 Milvus

同时把端口避让改成 ${MYSQL_PORT:-3307}:3306，让 .env 成为唯一事实源。

→ 顺带解决镜像臃肿

pyproject.toml 里 streamlit>=1.36 还是主依赖（V1 遗留，V2 完全不用）， flagembedding / sentence-transformers 会拖进 torch。 Dockerfile 直接 pip install "." → 镜像 3GB+，而单容器演示根本不需要这些。

拆 optional extras：[project.optional-dependencies] rag = [...]， 基础镜像只装 fastapi/langgraph/sqlglot，镜像体积能砍到 1/3。演示启动会明显变快。

05P1　"用起来流畅"的五个堵点

1

导航 11 项平铺，31 个岗位看到一模一样的菜单

app.js:670 renderNav() · NAV_ITEMS 无角色过滤

你自己的 docs/V3-UX优化方案.md 里写得很清楚："操作工只需 3 个功能却面对几十个菜单 = 信息过载"。 但 V3 那轮落地了简报横幅、KPI 下钻、问数历史、常用语（我逐个查了，都在），唯独导航角色化没做。

改法：给 NAV_ITEMS 的每项加 roles: []（空 = 全员）， renderNav() 按当前角色过滤。31 个岗位里，生产一线（mt/wh/whm/ehs）应该只看到 3-4 项。 数据来源直接用 P0-2 那份 nav_scope，不做第二份映射。

这是投入产出比最高的一项：改 30 行，演示观感立刻不一样。

2

健康检查是假阳性，"后端已连接"不可信

api.py:134 · 返回硬编码 {"status":"ok"}

这个端点不探测 DB、不探测 Milvus、不探测 Redis、不探测 LLM。 也就是说 所有依赖全挂，它照样返回 ok。Docker 的 HEALTHCHECK 和将来的 K8s 探针都会当真。

更麻烦的是前端：顶栏那个"后端状态"圆点探的就是它。所以演示时圆点变绿， 只代表 uvicorn 进程活着，不代表问数能出结果。

改法：改成结构化依赖探针，各项独立降级：

{ "status": "degraded",
  "checks": { "db": "ok", "redis": "ok", "milvus": "down", "llm": "down" },
  "latency_ms": { "db": 3, "redis": 1, "milvus": 2001 } }

前端圆点分三色：ok 绿 / degraded 黄（"部分能力降级"）/ down 红。 客户看到黄灯会觉得你专业，看到绿灯但其实查不出东西才会觉得你糊弄。

3

首屏 600KB 未分包，公网隧道要等 4 秒

demo-data 211KB + screens 210KB + office 36KB + app.css 109KB

你在 index.html 注释里已经踩过这个坑（"白屏从 ~12s 降到 ~4s"，靠 defer + GZip）。 但根因没解：demo-data.js 和 screens.js 各 210KB，且是同步加载的。

改法（按性价比排序）：

  • 把 DEMO_TODOS / ORDERS / SPC_DASHBOARD / ALERTS / REPORTS 这些纯演示常量 拆成 demo-data.dashboard.js / .chat.js，navigate() 时按屏懒加载。 首屏只需要 ROLES + ROLE_KPIS，能砍掉 150KB+。
  • 给静态资源加 Cache-Control: public, max-age=31536000, immutable。你已经用 mtime 做版本号了， 说明本来就想长期缓存——现在是矛盾的做法。
  • 服务端 gzip_static 或预先压好 .gz，省掉每次请求的压缩 CPU。
4

api.py 单文件 958 行 / 约 40 个路由，全部挂在 app 上

无 APIRouter 拆分 · OpenAPI 无 tags 分组

这不只是代码整洁问题。你用 /docs 给客户做接口演示时，现在是一坨 40 条的平铺列表。 按域拆成 router + tags，OpenAPI 首页立刻变成一张产品能力地图：

顺序按用户任务流排，不按技术分层排——这是"产品展示更清晰"最直接的一招，且零业务风险。

5

版本号三处不一致，客户会问"这到底是 V2 还是 V3"

08改造顺序

排序原则：先堵会静默出问题的坑，再做演示观感，最后做结构美化。反过来做等于给漏水的船刷漆。

序动作风险改动面做完能解决什么
1 WorkflowEngine 硬校验 + 解耦 WORKFLOW_DB 极低 约 10 行 + README 堵住"切 MySQL 静默丢工单"，这是唯一会造成数据事故的坑
2 健康检查结构化 + 前端三色状态 低 api.py 1 个函数 + app.js 演示时"降级"变可解释，而不是看起来像挂了
3 导航角色化过滤 低 NAV_ITEMS + renderNav 31 岗位菜单不再同构，观感提升最大的一项
4 数据范围目录 + 四个看板接 role 中 新 YAML + dashboard.py 堵住"HR 看 SPC"的合规质疑，同时给第 3 步提供数据源
5 合并 compose + env_file + profiles 中 两个 yaml → 一个 Docker 路径第一次真正能跑生产形态
6 api.py 拆 router + OpenAPI tags 低 纯搬迁 /docs 从"40 条平铺"变成产品能力地图
7 WorkflowRepository 抽象 中 新契约 + 搬迁 架构叙事自洽（四契约），并为 MySQL 铺路
8 依赖瘦身 + 前端分包 + 三个 god module 低 纯搬迁 镜像体积、首屏时间、长期可维护性
9 真正写入 MySQL + 签名表唯一索引 高 新仓储实现 多实例 / 高可用。客户不要求就别做
✓ 1-3 步加起来不超过两天，但能解掉全部"会翻车"的风险

如果现在就要拿去见客户，做完 1、2、3，你就没有硬伤了。4 是锦上添花（真被问起就说"数据范围目录在下一迭代"）， 5 取决于客户要不要 Docker 交付，7-9 是技术尽调通过后的活。

09明确不要动的部分

架构评审最容易犯的错是"顺手重构"。这几样东西别碰，它们是资产不是负债：

  • 场景 YAML 的声明式范式——7 个场景零代码新增，这是最有说服力的架构证据，改成 Python 编排就是自毁。
  • PermissionRegistry 的构造期自检——"Agent 持 *.approve 直接启动失败"这种 fail-fast 设计，比任何文档都有说服力。
  • 587 条离线确定性测试——探针恒 False、不发外网。这是你敢做上面所有搬迁的底气。
  • Text2SQL 八道防线 + provenance——"数字从哪张表哪条 SQL 来全程可追溯"是真正的护城河，别为了性能削它。
  • 零构建前端——HTML/CSS/JS 直接挂 FastAPI，没有 npm、没有打包。演示分发极其方便。P1-3 说的分包是文件级拆分，不要趁机引入 webpack/vite。
  • SPC 纯函数内核——不经过 LLM 算 Cpk，缺数据强制人工确认。这个纪律比功能值钱。

10一句话收尾

你的问题是"宣称"跑在了"实现"前面一步，不是设计能力不够。 把三处宣称对齐（MySQL 可切 / 全员可见 / 一条命令部署）， 再把 11 个屏按用户任务流重排一次，这个产品的对外说服力会跨一个台阶。

相反，如果再往上堆智能体和场景，而这三处不对齐，客户做技术尽调时一处失分就会连累全部——包括那些真正做得好的部分。
