## 4. 演示边界：能证明什么 / 不能证明什么

### 能证明（每条都有可复跑的证据）

- **权限过滤发生在召回之前**：把可见集压到 1 条案例、k=50，只返回那 1 条；用受限案例原文当 query、
  k=1，在适配器层仍只回可见案例（§2.3、§3）。
- **候选不足如实返回、不补齐**：k=200 时 qa 得 148 条、equipment 得 134 条，`padded=false`，
  notice 原文含"已如实返回，不放宽过滤补齐"（§3、§5.2）。
- **无权与不存在不可区分**：两条 404 路径的 SQL 语句模板与调用次数**完全相同**（delta = 0/0），
  真实 HTTP 响应体**逐字节一致（106 字节）**，耗时比 P50 **0.97×**（§7.4）。
- **原始来源单号不进检索响应**：命中载荷只有不可反推的 `source_ticket_ref`，真号仅在详情接口
  满足权限且密级达标时返回，并带 `X-Case-Trace: full`（§8）。
- **引用可验证且文本漂移被拒**：改文本不 bump 版本 → 该条断言被拒（`text_hash` 不一致），
  其余断言保留、仍作答（§5）。
- **跨部门授权有闸门**：自审批被 `AccessSelfApproval` 拒绝且**无副作用**；受限清单对密级 1/2/3
  三档主体**均不含涉密案例**（§13.1、§13.2）。

### 不能证明（评审据此决策，不要高估）

1. **检索质量只是一条基线，不是产品水平**。demo 级实现（`blake2b` 1–2gram + 0.6 余弦 / 0.4 关键词）
   在 12 条固定样本上的**真实**口径为：`recall_rate 0.667`、k1 / k3 / k10 / mrr 均 **0.667**、
   `answer_rate 0.833`。**架构文档 §12 里的 k1≥0.75 / k3≥0.90 / k10≥1.00 是远期目标，不是本次验收线**——
   实际差距约 **33%**。（§5.1、§16.5.5）
2. **这组数字曾经骗过人，而且骗得越差越好看**。早期版本的评测脚本把**召回失败的样本排除出分母**
   （`rank=None` 即未召回），于是 12 条里 4 条失败被静默剔除，"剩下 8 条"全部命中 top-1，
   k1/k3/k10/mrr 报成 **1.0**——**召回退化会让指标变好**。已改为"未命中按最差计入"+ 新增
   `recall_rate` 显式指标。**这条是本报告可信度边界的最短说明：任何"过滤掉失败样本"的统计，
   都要先回答"被排除的是不是恰好最该计入的那批"。**（§16.5）
3. **拒答阈值是标定值，不是普适值**。`answer_min_score=0.18` + `answer_margin=0.05` 是
   **对当前 99 例语料**标定的；换语料或换模型**必须重标**（入口 `tools/calibrate_answer_thresholds.py`）。
   现在能撑住演示，靠的是**问句与案例文本高度同源**（不少 query 直接取自案例 `phenomenon` 原文）；
   **标定结果不能直接当验收标准**。（§5.1、§16.2）
4. **词表外人名目前拦不住**（`CASE_REDACTION_EXTRA_TERMS` 默认覆盖率 0），见上线清单第 1 条（§4.4）。
5. **只有 memory 后端被实测过**：`chroma / milvus` 为惰性 import，demo 未验证（§11-A5）。
6. **受限清单是有意披露**：搜不到但"看得见标题"意味着**能确认这些案例存在**——这是新的存在性侧面，
   详情接口仍不可区分，但检索侧有意开了口。**需产品/安全签字**（§13.3）。
   跨部门访问申请也是**窄口径**：仅 `active/deprecated`、非涉密、单一审批人 + TTL，无多级审批链（§13）。

## 5. 三条最能改变决策的事实（不粉饰）

1. **一个会自我美化的指标**：召回率退化 → 失败样本被剔除 → 指标变好。
   这比没有指标更危险，因为它提供的是**虚假的安全感**（§16.5）。
2. **一个"看起来在工作、其实没有"的守卫**：残留守卫曾因定义顺序而恒真（永远查不出残留）；
   改成 teardown 后**当场抓到两个真 bug**（自清理漏删主表行、误删种子案例）。
   这类失效不会让测试变红，只会让**回归防护变成摆设**（§15.5、§16.2c）。
3. **一个被实测推翻的推测**：我曾建议加"姓氏+一两字名字"的弱规则兜底，实现者实测出 **82 处误伤**
   （"SMT 段锡膏""重新张紧并"），改为"必须带职务上下文"后 99 例语料 **0 误报**。
   结论因此改为：**弱规则只能产待办，绝不能自动脱敏**（§4.4）。

另需评审知晓：**验收方也会看漏**——我曾只 grep 根 `README.md` 就误判实现者文档没交付。
**验收方误判与实现方漏交付后果一样重**：后者让缺陷上线，前者让做对的工作被要求重做（§16.4）。
