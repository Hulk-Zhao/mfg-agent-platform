# R14 场景屏 S07–S11 去留决策（D16）

> 决策日期：2026-10-22
> 决策范围：生态链演示场景屏体系（`demo/ui/scenes/` + `data/demo_storyline/frontend/`）
> 依据：PRD Q5 方案 B（暂缓 S07–S11，先以 R1 对话闭环承载）、架构建议 D16、
> 风险清单第 10 条（决策记录须含 `frontend/registry.json` 回放数据迁移结论）

## 一、结论摘要

1. **保留 S00–S06 共 7 屏**，作为交付物料原样维护，本轮零代码改动；
2. **S07–S11 五个屏位不建**；
3. **后续新场景一律以对话闭环承载**（问数 → 结论 → 待确认工单 → 留痕 → 报告），
   不再默认新建静态场景屏；
4. **`frontend/registry.json` 无需数据迁移**：S07–S11 从未产生条目或数据文件，
   现有 7 条场景登记与 15 个 objects 原样保留。

## 二、事实核对（决策前实读，不凭印象）

| 事实 | 证据 |
|---|---|
| 已交付场景屏 = 7 屏（S00–S06） | `src/mfg_agents/v2/demo/ui/scenes/` 下 `s00-skeleton.js`、`s01-intake.js`、`s02-npi-kickoff.js`、`s03-stage-gate.js`、`s04-batch-ecn.js`、`s05-trace.js`、`s06-procurement.js` |
| 登记表只有 7 条场景 | `data/demo_storyline/frontend/registry.json` 的 `scenes[]`：s00 / s01 / s02 / s03 / s04 / s05 / s06 |
| 场景派生数据只有 6 个业务屏文件 | `data/demo_storyline/frontend/` 下 `s01…s06-*.js`（s00 是契约样本屏，`data: null`） |
| S07–S11 **没有任何规格** | `docs/制造生态链-demo-AIGC开发顺序计划-v1.0.md` 的 T06–T11 只覆盖 S5 / S1 / S6 / S4 / S2 / S3；全文检索 `S07|S08|S09|S10|S11` 只命中「规划 12 屏」的 registry 注释与架构/PRD 决策项 |
| 「12 屏」是容量预留，不是内容规划 | `scenes/registry.js` 首部注释「共 12 个（S00–S11）」；`id` 校验只要求 `^s\d{2}$`，无场景主题清单 |
| 现有 7 屏对应订单主线闭环 | S1 接单评审 → S2 立项 → S3 阶段门 → S4 批量监控与 ECN → S5 出货与质量追溯 → S6 采购执行（S00 为契约自检屏） |

> 结论的前提：S07–S11 没有业务主题、没有数据契约、没有验收口径。以「补齐编号」
> 为目的新建 5 个屏，只会产生无数据来源的壳屏，违反「不编造」纪律。

补充口径：

- 上述 5 个屏位若未来确有需求，**必须重新走一遍立项**：主题清单、数据契约
  （objects 从 jsonl 实读）、验收脚本、岗位可见性四项齐备才准入；

  但它是**契约验收样本**，不含业务结论；业务屏占位会误导演示解说。

## 四、新场景的承载方式（替代方案）

新场景默认走对话闭环，复用已交付能力，不再新增静态场景屏：

| 场景环节 | 承载机制 | 已落地证据 |
|---|---|---|
| 提问与取证 | 统一问数（两级路由 + Text2SQL 注册查询 + 字段脱敏） | R4 / 数据口径词典 R8 |
| 交期与承诺 | 交期答复确定性成稿、对客承诺进 HITL | R5 |
| 齐套与催交 | 催交状态机 + 演示回写徽标 + 连接器回执 | R6 / R13 |
| 质量追溯 | 批次三路并查（traced / partial / no_data） | R7 |
| 经营问答 | 大单进度、主动风险 | R10 |
| 资金类处置 | 呆滞料盘点 + 退供评审（interim 闸门，Agent 不放行） | R11 |
| 治理留痕 | 审批确认中心（槽位 + 会签 + 终批） | R3 / R9 |

准入条件（满足任一才考虑新建场景屏，且需架构评审）：

1. 交付现场**无网络 / 无登录条件**，必须离线播放静态长图；
2. 同一场景需要**脱离对话**做固定讲解（展会大屏、投标材料）；
3. 客户明确要求「一屏讲清一条价值链」，且数据契约可从现有 15 个 objects 取全。

复核节奏：按 PRD Q5，**一个季度后按实际使用数据复核一次**；无新增使用证据则不重开。

## 五、`frontend/registry.json` 回放数据迁移结论

**结论：不迁移、不删除、不改名。**

| 项目 | 处置 | 原因 |
|---|---|---|
| `scenes[]` 的 s00–s06 条目 | 原样保留 | 对应屏文件与测试（`tests/demo/test_s01..s06.py`、`test_t05_contract.py`）均在用 |
| `objects` 15 个条目 | 原样保留 | 与 `data/demo_storyline/*.jsonl` 文件名一一对应，装载层 `/api/v2/demo/objects/{name}` 现取 |
| S07–S11 的条目 / 数据文件 | 不存在，无需迁移 | 从未创建；`frontend/` 下无 `s07…s11-*.js` |
| 回放接口 `/api/v2/demo/replays/{replay_id}` | 不受影响 | 回放包来自 `agent_replays.jsonl` / `rag_replays.jsonl`，与场景屏登记相互独立 |
| 场景脚本加载顺序 | 不变 | `index.html` 只加载 s00–s06；新增屏才需要追加 script |

若未来因合规/去品牌化必须下线某屏，迁移顺序固定为：
① 先删 `registry.json` 对应条目 → ② 删除/归档 `frontend/sNN-*.js` →
③ 删除 `scenes/sNN-*.js` 与 `index.html` 引用 → ④ 删除 `tests/demo/test_sNN.py`，
并同步更新本文档。**禁止只删代码不删登记**（会导致导航引用空模块）。

## 六、对现有资产的处置

- S00–S06 的屏文件、数据契约、测试与徽标纪律**全部保持现状**；

  「交付 S00–S06；S07–S11 已决策不建」，避免后续窗口按旧注释补屏；
- 不新增 `s07…s11` 任何文件、不改 `app.js` / `scene-kit.js` / `app.css`。
