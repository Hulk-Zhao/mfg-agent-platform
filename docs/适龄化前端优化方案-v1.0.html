01核心结论

本轮对前端做了逐行实测（app.css 4500+ 行、app.js 1300+ 行），共定位 32 项可验证缺陷，其中 12 项属于「看不见 / 点不到 / 不知道自己在哪」的功能性阻断，而非审美问题。

三项结论改变了问题的定性：

3.5 : 1

最该被看见的按钮，标签本身看不清

主按钮 .btn-primary 是白字压在 #2B7AE0→#3B8AE8 渐变上，对比度仅约 3.5，低于正文级 4.5 门槛。根因是 --primary 一个令牌同时承担两种相反职责：做强调文字要亮，做按钮填充底要暗。解法是拆成「墨色」与「填充」两个角色令牌。

2.99 : 1

亮色主题自落地起就没真正达标

亮色下 --text-3 对白底仅 2.99、侧栏分组标题 2.40、登录页副文案 2.59。这些颜色确实存在于已提交版本中——讽刺地来自名为「亮色对比度回修」的那次提交。只修深色、把资深员工推向亮色，反而更糟。

≠ 放大字号

资深员工的最优解是换主题，不是放大字号

老视（45 岁后调节力 <3D）伴随瞳孔散大与球面像差，深色模式下的光晕（halation）无法通过放大字号消除。正确落点是「亮色 + 大字 + 宽松密度」打包档位。这条决定了整个方案的形态。

一句话结论：当前界面是按「25 岁、深色环境、高信息密度」的单一假设设计的，而企业内 45 岁以上用户恰恰在这三个维度上全部相反。改造不是把字调大，而是让主题、字号、密度三件事可以被一次点击同时切换，并且让不会主动找设置的人也能在真实阅读场景里遇到调整入口。

03三类用户画像

青年员工
22 – 32 岁 · 数字化原生
视觉生理
调节力 8–10D，近点约 10cm，10–11px 小字无阅读障碍；对比敏感度处于峰值。
操作习惯
鼠标精度高，可命中 ≤24px 目标；惯用快捷键与多标签并行；滚动耐心高，愿意长页面探索。
认知特点
短时记忆 7±2 项，可同屏处理 3–4 个卡片；术语（Cpk / OEE / HITL）学习成本低；出错后自主恢复强。
核心诉求
关键路径 ≤3 次点击；支持功能搜索直达；允许高信息密度；键盘可达且焦点环完整。
中年员工
33 – 45 岁 · 业务骨干
视觉生理
调节力降至 4–6D，38–42 岁出现早期老视；对比敏感度中高频衰退最早——最先表现为「看不见卡片边界」；晶状体轻微黄化。
操作习惯
鼠标仍精准但滚动耐心显著下降，倾向「看标题 → 定位 → 读重点」；用 Ctrl+F 与筛选多于滚动；多任务并行，易被打断。
认知特点
领域 expertise 高，术语无障碍但反感冗余解释；短时记忆被业务负载占用，同屏分组过多会丢失当前位置。
核心诉求
正文 ≥14px、辅助 ≥12px；控件边界 ≥3:1；每屏有明确「我在哪」；一级区块 ≤5 个。
资深员工
46 – 60 岁 · 经验权威
视觉生理
老视全面化（调节力 <3D，近点退至 40–50cm）；晶状体黄化使蓝光透过率下降约 30%；需 ≥7:1 才能舒适阅读小字；暗光下瞳孔散大 → 球面像差 → 深色模式光晕；男性红绿色弱累计约 8%。
操作习惯
鼠标抖动，需 ≥44px 目标；滚动耐心低，倾向线性从左到右点击；几乎不用快捷键；触屏经验薄弱，误触后不知如何退出；8px 滚动条难以抓取。
认知特点
行业经验深厚但不熟数字化术语，偏好中文全称；短时记忆 4–5 项，跨屏/滚动后易丢上下文；出错后恢复能力弱，依赖明确的撤销与返回。
核心诉求
默认落「亮色 + 大字」；可点目标 ≥44px；状态必须色 + 图标 + 中文三重冗余；每个不可逆动作有固定位置的撤销入口。
设计上的关键取舍：不要用「青年 / 中年 / 资深」给档位命名。年龄与实际视力弱相关（同年龄段差异可达 3 倍），贴年龄标签既冒犯又不准。本方案统一用诉求命名：标准 / 清晰 / 大字，并用症状化提问（「要凑近一点才看得清」）而非年龄提问来引导选择。

05优化方案（按维度）

5.1 色彩对比度

结构性改造：拆开 --primary 的双重职责

这是本方案最核心的一处令牌重构。--primary 现在同时承担 ① 深色表面上的强调文字（需要亮）与 ② 实心按钮填充底（需要暗以承载白字），两者要求相反，这正是 C1 与 C4 同时失效的根因。必须拆成两个角色令牌：

  • --primary = 强调墨色（亮方向）
  • --primary-fill-a/b + --primary-ink = 实心按钮（亮蓝底 + 近黑字）
令牌现状改造后（深色）改造后（亮色）效果

--danger#F4696B#FD9496#B8202B5.07 → 7.06 AAA
--text-3#93A8C6#A3B6D0#656E7E6.20 → 7.28 / 2.99 → 5.14
--border-control（新增）无#5A80B2#818A9D1.40 → 3.70 PASS 3:1

--focus-ring（新增）半透明 rgba#6BAEF7#1557AD2.09–2.92 → 6.46–7.99
为什么装饰边框不推到 3:1：WCAG 1.4.11 只要求必要控件边界达 3:1，装饰性分隔线可豁免。强行把 --border 提到 3:1 会把深色主题做成「描边面板」，是视觉灾难。正确做法是新增 --border-control 专供输入框、下拉、复选、表格列线使用。

亮色侧栏割裂的处理

「品牌深色侧栏」在白色内容区旁会让瞳孔在每次视线横移时重适应，对调节慢、暗适应差的资深员工是持续性负担。方案是把侧栏与登录页从硬编码渐变改为令牌驱动，亮色下跟随变浅；深色模式下完整保留原有渐变与品牌资产。同时修复 7 处历史失效色，统一改用 var(--text-3)（实测 4.45–5.14，全背景 AA）。

中文字体与排版规则

  • 字重陷阱：企业内网以 Windows 为主，Microsoft YaHei 只有 400 与 700。写 600 会被合成为 Bold，导致「13px 加粗标题」与「16px 标题」视觉撞车、层级崩塌。规范：正文只许 400，强调只许 700，500/600 仅用于 ≤14px 的小面积控件。
  • 字间距：中文正文 letter-spacing: 0（加字距会让方块字松散）。现状侧栏分组标题上的 letter-spacing: 1.2px 配 10.5px 中文是负优化，改为 12px + 0.5px。
  • 断行：启用 line-break: strict; overflow-wrap: break-word，严禁 word-break: break-all（会把「2024-Q3」断碎，造成阅读中断）。
  • 等宽数字：所有指标、表格、柏拉图数字启用 font-variant-numeric: tabular-nums。现状为比例数字，列不对齐，老视用户纵向扫读会串行、读错量级——低成本高收益项。

5.5 交互反馈

焦点环：不透明令牌 + inset 绘制

现状半透明 rgba(59,130,246,.65) 在四种背景上实测仅 2.09–2.92，全部不达标——所以准确表述不是「这 6 类有焦点环」，而是「这 6 类有焦点环形状，但指示强度不合格；其余业务级组件连形状都没有」。

更糟的是还有一整类伪装成焦点环的东西。全站另有 13 处用 box-shadow 半透明光晕代替焦点环（--ring-color #3B8AE8@.30、.of-* @.25、紫 #8B5CF6@.18、.case-onto-q @.14、--primary-light-2 @.11）。它们看起来"有反馈"，实测渲染对比度只有 1.16 – 1.55，比 outline 那处还差一个量级——「有」比「没有」更危险，因为没人会去修一个看起来正常的东西。改造分两层：

第一层：色值换不透明令牌。深色 --focus-ring #6BAEF7（vs 卡片 6.46 / vs 页面底 7.99），亮色 #1557AD（vs 白 7.00 / vs #F3F5F9 6.42），全部通过 3:1。

第二层：改用 inset 绘制。全站有 30+ 处溢出容器（.nav、.role-grid、.hitl-screen、.user-menu、.chat-scroll、.login-shell 等）。若统一用向外 outline，需逐个排查祖先容器、且 chip（34×24）这类紧凑元素的外扩环会互相重叠。而 box-shadow: inset 绘制在元素自身盒内，永不被祖先 overflow 裁切——一次免疫：

:where(a,button,input,select,textarea,summary,[tabindex]):focus-visible{
  outline: 2px solid transparent;  /* 高对比模式下由系统色接管 */
  box-shadow: inset 0 0 0 2px var(--focus-ring);
}

透明 outline 不能省：Windows 高对比 / forced-colors 模式下 box-shadow 会被丢弃，只剩透明 outline 由系统接管才能保证焦点不消失。!important 仅用于覆写既有的 outline: none，其余靠选择器权重取胜。

10.2 技术风险

  • 焦点环 4px 外扩在紧凑区溢出：64px 图标轨、chip、表格行内小按钮处会被父容器裁切或相邻互压 → 对这些区域提供内嵌变体并保证父级 overflow: visible。
  • 术语自动注入可能误伤：TreeWalker 扫描会把按钮文案里的「Agent」也包起来、破坏已有 title、与悬浮助手 DOM 冲突 → 先做白名单容器扫描，验收通过后再扩全量。
  • 增量方案依赖 renderNav() 的重绘时机：若未来导航改为增量更新，MutationObserver 方案失效 → 已写入验收第 19 条作为常驻回归测试。
  • 半透明 rgba 是这个项目的系统性习惯：凡承担「必须可见」职责的元素（焦点环、控件边框、错误描边）都应强制使用不透明色，否则会持续重复产生同类缺陷。
  • 改造约束：场景屏下沉必须沿用 SceneRegistry.register() 登记机制，不得回头改 NAV_ITEMS 字面量。现有运行时登记（规避架构守卫的正则解析）是正确的架构决策，改动字面量会弄红 test_架构守卫.py。
  • 登录页角色网格的滚动条是 6px 特例（通用为 8px），改造时极易漏掉——而它恰恰位于资深员工进系统的第一个交互上。
  • 覆盖层最容易踩的坑是特异性，不是选择器写得对不对。若用 :where() 写通用焦点规则，它贡献 0 特异性，整条会塌成（0,1,0）或（0,2,1），被 .btn:focus-visible（0,2,0）与场景屏运行时注入的 .case-input:focus（0,2,1）反压——文件后加载也没用，特异性优先于层叠顺序。必须带 html:root 前缀提权（可达 0,3,1），或在关键属性上显式 !important。症状是「文件改了、实际没生效」，而验收时肉眼极难发现，因为焦点环只在 Tab 时出现。
  • 焦点环不能只看 outline。本项目大量位置用 box-shadow 半透明光晕冒充焦点反馈（13 处，实测 1.16–1.55）。「有反馈」比「没反馈」更危险——没人会去修一个看起来正常的东西。凡做无障碍加固，必须把 box-shadow 一并纳入扫描范围。
  • 可聚焦性不完全由 CSS 决定。部分可点组件若是 <div>，仅补样式无效，还需 tabindex="0" + role="button" + Enter / Space 键盘处理；实施时须先确认 DOM 标签再选方案。
  • 登录页角色网格的滚动条是 6px 特例（通用为 8px），改造时容易漏掉——它恰恰位于资深员工进系统的第一个交互上。
