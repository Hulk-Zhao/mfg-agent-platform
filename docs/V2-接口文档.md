# mfg-agent-platform · V2 接口文档

> 版本：2.0.0（含 V2 增量：4 场景 + 脚手架对齐）
> 服务入口：`mfg_agents.v2.demo.api:app`（FastAPI）
> 运行：`uv run uvicorn mfg_agents.v2.demo.api:app --port 8004`
> 统一响应信封：`{"code": 0|非0, "data": <obj>, "message": "<msg>"}`（HTTP 层另含状态码，见"错误码"）

---

## 1. 概述

平台把"制造业多智能体协同"封装为**统一查询入口 + 事件流 + 人工在环（HITL）**三件套：

```
用户/IM → POST /api/v2/query ──► TwoLevelRouter（L0 规则 / L1 闭集 / 降级）
                              └► 场景 DAG（YAML 声明式）：
                                   intake → 域判定 → fan_out 并行取证 → fan_in
                                   → workflow 工单 → HITL 人工确认 → report
       GET /api/v2/events ──────► SSE 实时事件流（请求级隔离）
       GET /api/v2/workflow/pending ├─ POST approve/reject（HITL 回写状态机）
```

**离线可跑**：本机无 LLM（Ollama 离线）时自动降级——路由走规则、判定/报告走模板，
结论标 `degraded=true`，数字仍来自 SQL（`provenance` 可溯源），**绝不编造**。

---

## 2. 基础信息

| 项 | 值 |
|---|---|
| Base URL | `http://<host>:8004` |
| 数据格式 | 请求 `application/json`；SSE 响应 `text/event-stream`；企微回调 `application/xml` |
| 认证 | demo 无鉴权；`user_ctx` 由调用方注入（生产应由认证体系填充） |
| 权限模型 | 表级白名单（`TABLE_ACL`）+ 列级脱敏（`SENSITIVE_COLUMNS`，按角色），fail-closed |
| 场景枚举 | `line_stop_v2` / `incoming_quality_v2` / `customer_complaint_v2` / `delivery_status_v2` / `equipment_warning_v2` |

| 端点 | 方法 | 说明 |

| `/demo-ui/*` | GET | 演示前端静态资源（`demo/ui`） |

## 4. 端点详情

### 4.1 `GET /api/v2/health`

结构化依赖探针。**不触发编排器初始化**（不建库、不加载场景、不连向量库），
可被 Docker `HEALTHCHECK` 与前端顶栏高频调用。

**5 项探针并行执行**（`ThreadPoolExecutor`），总耗时 = 最慢的一项而非各项之和；
TCP 探测共用一份 0.6s 的**总预算**（不是每地址族各算一次，`localhost` 会同时解析出
`::1` 与 `127.0.0.1`，按每地址超时算会翻倍）。实测 Milvus 未起时该端点约 0.6s。

**响应**
```json
{
  "status": "degraded",
  "mode": "degraded",
  "version": "2.0.0",
  "degraded_components": ["vector"],
  "checks": {
    "business_db": { "state": "ok",       "detail": "业务库只读连接正常", "ms": 0.9 },
    "workflow_db": { "state": "ok",       "detail": "治理库只读连接正常", "ms": 0.5 },
    "redis":       { "state": "ok",       "detail": "连接正常",           "ms": 90.1 },
    "vector":      { "state": "down",     "detail": "TimeoutError: localhost:19531 在 0.6s 内不可达（最后错误：timed out）", "ms": 606.2 },
    "llm":         { "state": "ok",       "detail": "deepseek 就绪",      "ms": 144.4 }
  }
}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `status` | `ok` / `degraded` | 全部就绪 / 服务可达但存在依赖降级。**不返回 `error`**——HTTP 200 已证明进程可达；把"依赖挂了"表达成不可达会让前端误判离线并退回演示数据 |
| `mode` | `full` / `degraded` / `offline` | 前端顶栏展示用。`offline` = 未配 LLM 的离线降级形态（规则路由 + 模板结论） |
| `checks[].state` | `ok` / `down` / `disabled` | `disabled` 表示未配置且设计上允许（如未设 `REDIS_URL`），**不计入降级** |

> 纪律：任一探针抛异常一律收敛为 `down`，健康检查自身不允许 500。
> 前端只判 `status ∈ {ok, degraded}` 即视为"后端可达"。实现见
> `v2/services/health.py`，回归用例见 `tests/v2/test_架构守卫.py`。

### 4.2 `POST /api/v2/query`

**请求体**
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 用户问题（自然语言） |
| `user_ctx` | object | 否 | 用户上下文；缺省用演示默认 `{dept:"manufacturing", roles:["manufacturing","coordinator"]}` |
| `request_id` | string | 否 | 事件流订阅 id；缺省服务端生成 |

**`user_ctx` 字段**
| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | string | 用户标识 |
| `dept` | string | 部门（参与表级权限判定） |
| `roles` | string[] | 角色列表（`coordinator` 为跨域总控取证角色；`sqe` 可见供应商等敏感字段） |

**示例**
```json
{
  "query": "A型号能发多少货",
  "user_ctx": { "user_id": "u-gm", "dept": "management", "roles": ["coordinator"] },
  "request_id": "req-abc123"
}
```

**响应**（`data` = `OrchestratorResult.to_dict()`）
| 字段 | 类型 | 说明 |
|---|---|---|
| `query` / `run_id` | string | 原始问题 / 本次运行 id |
| `route` | object | 路由结果：`{domain, scenario_key, confidence, level, entities, low_confidence, reason}` |
| `scenario_key` | string\|null | 命中场景；`null` 表示超出范围（转人工兜底） |
| `report` | string | 对客报告（S3/S4；脱敏）或人工兜底说明 |
| `internal_brief` | object | 内部简报（按场景聚合的关键结论） |
| `provenance` | array | 溯源：各域 SQL 原文/通道/命中行/耗时 + 节点耗时 |
| `hitl` | array | HITL 待确认卡片列表（`status=waiting_hitl`，绝不自动放行） |
| `workflow_tasks` | array | 工作流工单列表 |
| `timings` | object | 各节点耗时（ms） |
| `degraded` | bool | 是否处于降级（LLM 离线）模式 |
| `degraded_reasons` | string[] | 降级原因（可审计） |
| `fallback` | string\|null | 兜底标记（`manual_ticket`） |
| `elapsed_ms` / `error` | number\|null / string\|null | 总耗时 / 错误 |
| `request_id` | string | 回显请求 id（用于订阅事件流） |

**响应示例（S4 出货风险，离线 degraded）**
```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "query": "A型号能发多少货",
    "run_id": "run-xxxx",
    "route": { "level": "L0", "domain": "supply_chain", "scenario_key": "delivery_status_v2",
               "confidence": 1.0, "low_confidence": false,
               "entities": {"product_model": "A型号", "line_code": "SMT-1", "urgency": "normal"} },
    "scenario_key": "delivery_status_v2",
    "internal_brief": { "ATP承诺分析": "A型号 ATP=400pcs，订单需求=3500pcs，缺口=3100pcs，风险订单 2 单", "...": "..." },
    "report": "尊敬的客户：经核实，贵司订单当前受产能与物料因素影响，存在交付风险……",
    "hitl": [ { "kind": "delivery_commit", "status": "waiting_hitl",
                "prompt": "对客交期承诺确认", "approver_roles": ["业务经理"], "task_uid": "wf-xxxx" } ],
    "workflow_tasks": [ { "ticket": { "wf_id": "delivery_risk_flow", "status": "running", "...": "..." } } ],
    "degraded": true,
    "degraded_reasons": ["报告生成 LLM 不可用：模板化 + 禁词表兜底"]
  }
}
```

### 4.3 `GET /api/v2/events`

订阅指定请求的事件流（SSE）。

**Query 参数**
| 字段 | 类型 | 说明 |
|---|---|---|
| `request_id` | string | 必填，`POST /api/v2/query` 或 `/events/open` 返回的 id |
| `wait_s` | number | 最长等待秒数（默认 120，上限 300） |

**SSE 消息**：`data: {<event>}\n\n`，`<event>` 字段见下表；收到 `final`/`error` 后结束。

**事件枚举**（与 V1 完全一致，前端零改动）
| `type` | 关键字段 | 说明 |
|---|---|---|
| `agent_start` | `node, label, icon` | 节点开始 |
| `tool_start` / `tool_end` | `tool, detail` | 工具调用（SQL/RAG/意图识别） |
| `llm_start` | `detail` | LLM 推理开始 |
| `agent_end` | `node, label, summary, status, elapsed_ms` | 节点结束（`status ∈ ok/degraded`） |
| `fan_in` | `node, domains, degraded, summary` | 并行汇聚 |
| `error` | `detail` | 异常 |

**错误**：`404`（`request_id` 不存在或已结束）。

### 4.4 `POST /api/v2/events/open`

**请求体**：`{ "request_id": "req-abc123" }`
**响应**：`{"code":0,"data":{"request_id":"req-abc123"},"message":"ok"}`
> 幂等：与 `query` 内的队列预开共用同一队列。

### 4.5 `GET /api/v2/workflow/pending`

**身份**：`Authorization: Bearer <token>`（无令牌 → `401`）。
**Query**：`role`（可重复或逗号分隔）——**只能收窄**视野，必须 ⊆ 令牌角色；试图传别人的角色 → `403`；角色无法识别 → `400`。

可见范围由「我是否持有该 HITL 槽位的权限」决定（判据来自 `v2/data/permissions.yaml`，见 `services/workflow_scope.py`）：

| `visibility` | 含义 | 可操作 |
|---|---|---|
| `mine` | 当前阶段轮到我（`action_for()` 非空） | 是 |
| `domain` | 我治理域内但暂不轮到我，或未纳管的历史存量（无主池） | 否（只读） |

**无治理职责的岗位**（如行政人事）返回 `data: []` 且 HTTP `200`——这是「本来就没有你的活」，与「无权查看」（403）是两种不同状态，调用方应分别提示。

**响应**
```json
{ "code": 0, "message": "ok",
  "data": [
    { "task_uid": "wf-xxxx", "wf_id": "hitl_disposition", "title": "退换货/特采决策确认",
      "status": "waiting_hitl", "priority": "P1", "assignees": ["SQE","PQE","生产"],
      "context": { "run_id": "run-xxxx", "kind": "disposition", "card": { "...": "..." } },
      "hitl_prompt": "退换货/特采决策确认", "sla_due_at": "2026-10-17T02:00:00+00:00",
      "visibility": "mine", "my_action": "select_action",
      "history": [ { "action": "create", "from": "pending", "to": "waiting_hitl" } ] }
  ],
  "scope": {
    "roles": ["sqe"], "slots": ["disposition"],
    "counts": { "mine": 5, "domain": 267, "visible": 272 },
    "filtered": true
  } }
```

> `scope.counts` **不含**不可见工单的数量：数量本身也是信息，不应成为权限的探测面。

### 4.5a `GET /api/v2/workflow/{task_id}`

单工单详情（会签后局部刷新卡片用）。可见性与 4.5 同源：

- 无令牌 → `401`
- 跨治理域（拿到了 ID 但不在我的槽位内）→ **`404` 而非 `403`**：403 等于确认「这个工单存在，只是你看不到」，会把 ID 空间变成可探测信息。

**响应**：`data` = 工单对象（结构同 4.5 的单条）。

### 4.6 `POST /api/v2/workflow/{task_id}/approve`

**请求体**
| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `approver` | string | `"演示用户"` | 审批人（写入工单 history） |
| `comment` | string | `""` | 审批意见 |
| `final` | bool | `false` | `true` 时终态 `done`，否则回到 `running` |

**响应**：`data` = 更新后的工单对象。**错误**：`404`（工单不存在）、`409`（非法状态迁移）。

### 4.7 `POST /api/v2/workflow/{task_id}/reject`

**请求体**：同 4.6（`final` 忽略）。
**响应**：`data` = 更新后的工单对象（`status=closed`）。**错误**：`404` / `409`。

### 4.8 `GET/POST /api/v2/im/wecom/callback`

- **GET**（URL 校验）：query 参数 `msg_signature, timestamp, nonce, echostr` → 验签+解密 → 回显明文。
- **POST**（消息处理）：解密 → `V2Orchestrator.handle` → 被动回复卡片（XML）。
- **错误**：`403`（验签失败）、`500`（未配置 `IM_TOKEN/IM_AES_KEY/IM_APPID`）。

### 4.9 看板：`GET /api/v2/dashboard/{manufacturing|quality|orders|spc}` 与 `GET /api/v2/dashboard/drill`

**鉴权**：必须带 `Authorization: Bearer <token>`（`POST /api/v2/auth/login` 换取）。业务聚合
不接受匿名读取——`/demo-ui` 的多岗位导航只是展示层，接口层独立裁决。

**数据范围裁决**（`v2/data/data_scope.yaml`，fail-closed）：

| 情形 | HTTP | 说明 |
|---|---|---|
| 缺令牌 / 令牌非法或过期 | `401` | `detail="缺少访问令牌"` 等 |
| 目录未声明该看板 | `403` | 新增看板忘了登记 → 谁也用不了（刻意如此） |
| 岗位不在该看板 `allow_roles` | `403` | `detail` 为对象：`message` / `dashboard` / `roles` / `allowed_roles` |
| 有权限 | `200` | `data` 为看板载荷，信封另带 `scope` |

**响应信封**

```json
{
  "code": 0,
  "data": { "screen": "orders", "kpis": [], "rankings": [], "risk_orders": [] },
  "message": "ok",
  "scope": { "dashboard": "orders", "roles": ["warehouse"], "masked": ["客户名称", "客户等级"] }
}
```

`scope.masked` 是本响应**实际命中**的脱敏字段标签（未命中不列，避免"声称脱敏但其实没这根路径"）。

**字段脱敏**（当前作用于订单看板的客户身份）

- 客户名称 → 稳定代号（`客户 A` / `客户 B` …，按该批数据字典序分配，同一客户在其他客户
  出现变化前保持同一代号）；客户等级 → `—`。
- 排行行与下钻明细**同源脱敏**：`rankings[key=otd].items[]` 的规则自动推导到
  `drill` 的 `rows[]`，不存在"排行看不到、下钻全列出来"。
- 被脱敏的行会**移除下钻实体**并标 `masked: true`：只藏名字而留下 `customer` 键，
  点一下就按真值查回来，等于没脱敏。前端据此取消该行的点击区。

**`/drill` 参数**：`screen` + `kpi` 必填，实体参数按指标维度通用取用（`line` / `model` /
`wo` / `customer` + `level` / `supplier` / `test_type` / `warehouse` / `wf` 等），
`step` → L4、`+station` → L5、`defect_type` → 不良类型下钻。层级跳级或维度组合非法 → `400`。
裁决与看板**同源**（`screen` 复用看板 key），否则就是一条"看板进不去、下钻却能拿"的后门。

### 4.10 现场看板：`GET /api/v2/site-board` 与两个回写端点

客诉 8D 场景在四域汇聚后由 `dispatch_site` 节点归因责任工段（显式工段 → 产线前缀 →
批次反查），并经 `NotificationService` 落到 `site_board_push` 表——现场看板就是这张表的
读取面与回写面。三个端点**同一份裁决**（`data_scope.yaml` 的 `site_board`，角色集合与制造
看板同源）与**同一条脱敏规则**（`rows[].customer`）。

| 端点 | 参数 / 体 | 说明 |
|---|---|---|
| `GET /api/v2/site-board` | `stage`（SMT/PCM/PACK/整机，缺省全部）、`status`（pushed/acked/closed，缺省全部） | 推送队列，按创建时间倒序；非法取值 → `400`（不静默当"全部"） |
| `POST /api/v2/site-board/{push_id}/ack` | `{"note": "…"}`（可选） | 现场接收（`pushed → acked`），接收人取自令牌身份 |
| `POST /api/v2/site-board/{push_id}/feedback` | `{"feedback": "…"}`（**必填**） | 现场处置闭环（`acked → closed`），结论写入留痕 |

**门禁顺序**：令牌（`401`）→ 岗位范围（`403`）→ 参数（`400`）→ 推送行不存在（`404`）→
状态机非法流转（`409`）→ `200`。**绝不把越权伪装成空数据**。

| 情形 | HTTP |
|---|---|
| 缺令牌 / 令牌非法 | `401` |
| 岗位不在 `site_board.allow_roles`（如行政人事） | `403`（`detail.dashboard="site_board"`） |
| 未知 `stage` / `status` | `400` |
| `push_id` 不存在 | `404` |
| 未接收就闭环 / 闭环后再次接收 | `409` |
| 闭环结论为空（含纯空白） | `400` |

**响应信封**（与看板同构）：`data = {"stage": …, "rows": [ … ]}`，
`scope = {"dashboard": "site_board", "roles": [...], "masked": [...]}`。
回写端点返回**同一信封**（单行），因此写响应也走脱敏——客户名藏在回写响应里等于没脱敏。

**脱敏**：`rows[].customer` 只对承担对客责任的岗位（`gm` / `sales` / `customer_service` /
`project_manager` / `finance` / `finance_manager`）可见真名，其余岗位看到稳定代号
（`客户 A` / `客户 B` …）。客户名**不内联进推送正文**——正文是自由文本，脱敏规则改不动。

**行级归属缺口**：当前按岗位裁决（"能看现场看板"= 整厂工段可见），尚未按组织/产线缩到
本人辖区（与四个看板同类缺口，见 README 生产化清单）。

### 4.11 预警中心：`GET /api/v2/alerts`（含第五类「现场推送」）

五类预警：`SPC越限` / `缺料` / `订单临期` / `设备告警` 由**当前只读业务数据**机械推导
（与三个看板、数据速查同源可对账）；第五类 `现场推送` 读**治理库**（`site_board_push`，
客诉 8D 分派后的现场处置队列）——业务库故障时前四类为空而它仍如实展示，这是设计
（它是分派的真实结果，不因业务库不可用而隐瞒），端点始终 `200` 带 `degraded:true` 骨架。

- **鉴权**：只需令牌（无令牌 `401`）。预警中心**全员可见**（异常可能来自任何岗位），
  故不走 `data_scope.yaml` 的看板白名单；
- **客户字段脱敏**：订单临期按 `orders`、现场推送按 `site_board` 的同一套规则脱敏
  （非对客岗位看到「客户 A」）——全员可见 ≠ 客户真名全员可见；
- **现场推送的字段口径**：`id` = `push_id`，`entity.push_id` / `entity.stage` /
  `entity.complaint_no` / `entity.batch_no` 供前端就地回写与审计留痕；
  `status` 取自现场真实回写（`pushed` → `待处置`、`acked` → `处置中`），
  `level` 为机械映射（客诉处置令 `P1`、8D 工单通知 `P2`）；
  **已闭环不进预警清单**（预警中心是"要做的事"，闭环历史走 `/api/v2/site-board`）；
- **绝不编造**：真实预警只给 `basis`（可复算的判定依据），不凭库中不存在的处置生命周期
  编造 `steps` / `timeline`；`rules` 随载荷回传五类判定口径供界面展示；
- **前端**：`demo/ui/screens.js` 的 `ALERT_TYPES` / `typeCls` 字面量必须与后端
  `services/alerts.ALERT_TYPES` 完全一致（`tests/demo/test_alerts_api.py` 有对回守卫）；
  现场推送卡片带写操作入口——「现场接收」打 `POST /api/v2/site-board/{push_id}/ack`，
  「闭环处置」先走必填结论弹窗再打 `POST …/feedback`，写完失效缓存并重绘（状态与
  筛选片计数即时同步）。

### 4.12 工段 → 现场群（企微）映射：`v2/data/im_groups.yaml`（无独立端点）

现场看板推送的**IM 触达**由 ``IMGroupNotificationChannel`` 完成：同一条通知在
`NotificationService` 上并联三路（日志留痕 / 站内看板 `site_board_push` / 现场群）。
工段与群的对应关系是**声明式配置**，不是新端点：

- **结构在 YAML**：`groups.<工段>` 声明群名 `name` 与 env 后缀 `slug`；工段必须来自
  `services.site_board.STAGES`（SMT/PCM/PACK/整机），写错即加载期失败
  （`IMGroupError`，与归因同一条纪律：**推错群比不推更贵**）；
- **凭据在 env**：群机器人 webhook key 走 `IM_GROUP_KEY_<SLUG>`，责任人 userid 走
  `IM_GROUP_MEMBERS_<SLUG>`（逗号分隔）；YAML 里不落真实值；
- **投递逐条记账**（`via` 为 `im_group` 的通知记录）：`pushed`（命中群/webhook 或
  应用消息）/ `skipped`（未配凭据、或 target 不是工段，附理由）/ `failed`
  （webhook 报错、凭据不齐，附理由）——**未配置不等于静默丢弃**；
- **应用消息（@ 责任人）发送链路**（`contracts/adapters/wecom.py::WeComPushClient`）：
  `gettoken(corpid+corpsecret)` → `message/send(touser+agentid+text)`，字段名与取值
  由测试逐项对回（企微按字段名解析，错一个字段就静默丢消息）；token 带 TTL 缓存
  （7200s，提前 300s 重取）；接口 `errcode≠0` 一律抛 `WeComTransportError`
  （推不出去让上层记账，**不静默当成功**）；传输层可注入（默认 stdlib `urllib`，
  测试用替身离线跑，不触网）。凭据三元组 `IM_CORP_ID`（缺省回落回调侧 `IM_APPID`）
  / `IM_AGENT_ID` / `IM_CORP_SECRET` 齐 → 默认运行时装配真实推送网关；缺一 → 网关为
  `None`，通道如实记 `failed`；
- **未做联调**：真实租户需在企微后台建自建应用、配好应用可见范围与 IP 白名单
  ——属部署动作，代码侧凭据齐即真发。

## 5. 数据模型：`QueryResult`（provenance 项）

`provenance` 数组中，SQL 类条目结构如下（供前端渲染"SQL 原文 + 命中行 + 脱敏标记"）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `channel` | string | `registered` / `metric` / `detail` / `compute` / `template` / `data_gap` / `report` / `workflow` / `hitl` / `rag` |
| `query_name` / `metric_id` | string | 查询/指标名 |
| `sql` | string | SQL 原文（可审计） |
| `row_count` | number | 命中行数 |
| `masked` | bool | 是否触发字段脱敏 |
| `tables` | string[] | 访问的表（权限审计） |
| `domain` | string | 产出域 |

> `data_gap` 条目：`{ "channel":"data_gap", "domain":"rd_engineering", "note":"设计根因：无 BOM/ECN/图纸数据源，未编造结论" }`
> —— 表示"该数据当前无来源"，前端必须显式渲染提示条（架构诚实性要求）。

## 6. 错误码

| HTTP | `code` | 场景 | 说明 |
|---|---|---|---|
| 200 | 0 | 成功 | `message="ok"` |
| 200 | 0 | 业务兜底 | 超范围问题：`data.fallback="manual_ticket"`、`data.scenario_key=null`（**不是错误**，是设计的一部分） |
| 400 | — | 参数非法 | 岗位未识别（`detail.unknown` 回显） |
| 401 | — | 未认证 | 看板/下钻/待办/工单详情未带令牌、令牌非法或过期 |
| 403 | — | 无数据权限 | 岗位不在看板 `allow_roles`（`detail` 给出谁能看）；或试图查询本人岗位之外的待办 |
| 403 | — | 回调验签失败 | 企微回调签名/AES 校验不通过 |
| 404 | — | 资源不存在 | `request_id` 无队列 / 工单不存在**或跨治理域不可见**（后者刻意用 404，避免确认 ID 存在） |
| 409 | — | 非法状态迁移 | HITL 状态机拒绝（如 `closed→running`） |
| 500 | — | 服务端错误 | 企微回调未配置密钥等 |

> 平台纪律：SQL 审核链拦截 / 越权访问 / LLM 生成 DDL 等**不返回 5xx**，而是降级为
> `fallback="manual_ticket"` + `warnings`（防"编得出、没人发现"）。
