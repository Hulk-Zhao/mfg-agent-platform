## 1. 产品定义

### 1.1 一句话

把六个生态链场景从「静态看板」升级为「**多智能体协同 + 检索增强**」的可演示形态：故事线事件驱动域智能体取证，案例/制度知识实时增强结论，需要人工决断时按治理槽位发起 HITL 工单，**全过程在屏上可见、可回放、可复现**——让观众看到「系统在协同」，而不是「页面在展示」。

### 1.2 产品目标（3 个，正交）

| # | 目标 | 衡量 |
|---|---|---|
| **G1 智能体过程可见** | 每个改造屏展示「智能体在干活」：ReAct 步骤、工具调用、证据链、并行分工，而非只给结论 | 改造屏 ≥1 个智能体协同面板，steps 与 `AgenticStep.to_dict()`（`v2/agents/agentic.py`）结构同构 |
| **G2 知识增强可解释** | 场景内嵌检索增强：相似案例（案例域 Agentic RAG）与制度问答（kbqa），**结论带出处、过滤可解释** | 每个检索结论可对回 `cases.jsonl`/`faqs.jsonl`；`filter_explain` 判定链可见 |
| **G3 协同治理闭环** | 事件 → 智能体取证 → 结论+证据链 → HITL 工单（按槽位可见）→ 屏上跟踪；五访客按岗位各看其该看的 | HITL 卡按槽位可见性实测（参照 T15 模式）；访客**零写操作** |

### 1.3 成功指标（可判定）

| # | 指标 | 判定标准 |
|---|---|---|
| M1 | **端到端闭环可演示** | P0 最深样板场景（S5）从客诉事件进入 → 智能体 trace → RAG 命中 → HITL 工单可见，累计界面操作 ≤3 次点击；其余五场景复用同模式（组件单测 + 各屏冒烟覆盖） |
| M2 | **演示可复现** | 确定性回放形态下，同一入口重复执行结果结构 100% 一致（回放数据由固定种子生成，参照 T02 字节级一致纪律） |
| M3 | **对账率** | 智能体结论中所有数字 100% 可对回 T02 数据包（`tests/demo/test_s05.py` 类断言扩展），屏内零编造 |
| M4 | **零回归** | `pytest tests/ -q` ≥ 1380 passed，只涨不跌；架构守卫 / 数据范围 / 待办可见性三类测试不许红 |
| M5 | **红线不破** | 隔离脚本（`tools/demo_gen/check_isolation.py`）全绿；屏内零写操作（无 POST/PUT/PATCH/DELETE）；徽标框架级强制（T12 守护）不破；五访客可见性从 registry 现算不破 |

### 1.4 核心设计决策：Agent 接入的「双形态」（本 PRD 的关键取舍）

**背景**：演示环境 LLM 可用性未定（`common/llm_factory` 走真实模型端点），而演示现场的第一要求是**可复现、不翻车**。

**决策 D1：区分两种形态，主链路按 (b) 保证演示可复现，同时预留 (a) 开关。**（用户 2026-10-20 裁决：确认 D1）

| 形态 | 定义 | 优点 | 风险 |
|---|---|---|---|
| **(a) 真实链路** | 走既有 `POST /api/v2/query` → TwoLevelRouter → 场景 DAG / 域智能体 ReAct 循环；SSE 事件流实时驱动前端 | 真智能上限；每次结论可能不同 | 依赖 LLM 端点与网络；现场超时/幻觉/跑偏即翻车；不可复现 |
| **(b) 确定性回放** | 服务端把智能体轨迹与结论**预计算**为演示数据（trace + steps + 结论 + 引用），前端展示与真链路**同构**的 UI | 可复现、零外部依赖、无幻觉、与「会签只读回放」既有范式一致 | 智能上限受限于预计算范围 |

**建议（本文立场）**：

1. **主链路按 (b)**：现场演示一律确定性回放。依据：① 平台既有六屏会签全部是只读回放（S1–S6 事实），双形态不破坏任何既有纪律；② 演示数据包已含 `cases.jsonl`（20 条脱敏案例）与 `faqs.jsonl`（11 条 FAQ，含 T02 追加的 DEMO-FAQ-011 接单评审会签），**回放数据源与真实 RAG 同源同构**，不额外造数；③ `demo/api.py` 的 `/api/v2/office/chat` 已有 `llm_available()` 不可用即诚实降级的先例，双形态切换有现成模式。
2. **预留 (a) 开关**（P1-1）：屏上「实时链路」入口，仅当 `llm_available()` 为真时可用，走 `/api/v2/query` + SSE，与 (b) 共用同一渲染组件。
3. **同构硬约束**：回放数据的 `steps` 结构必须与 `AgenticStep.to_dict()`（`v2/agents/agentic.py` L48-61：`step/thought/tool/args/summary/ok`）一一对应；前端**同一组件**渲染两种来源，仅数据来源标签不同（「实时链路」/「演示回放」徽标）——**不允许回放伪装成实时**。

## 4. 需求池

> 每条需求含：需求描述 / 验收标准 / 依赖 / 红线兼容性。
> **范围纪律（用户 2026-10-20 裁决）**：这是演示增强不是重写。**P0 = 六场景全量接入**（Q2 裁决，超出 PM 原「单样板」建议，工作量与回归面相应扩大，实施注意事项见 §4.4）；**S5 仍为最深样板**（选型理由见 §4.1），其模式（agentPanel + 案例 RAG 回放 + HITL 只读）作为 S1/S2/S3/S4/S6 的复制范式。
> **全局硬约束（每条需求的内嵌红线）**：① 五访客只读，任何新功能零写操作（写链路归治理窗口）；② 演示隔离（无外部连接串/真实企业名/电话，徽标框架级强制）；③ 前端零构建原生 JS，新屏/新组件走 SceneRegistry/SceneKit；④ 数字可对回 T02 数据包，不编数，装载层未就绪走降级文案；⑤ `pytest tests/ -q` ≥1380 passed 只涨不跌；⑥ 本机无 node，JS 语法校验以真机浏览器加载 + 括号闭合巡检测试兜底。

### 4.1 P0：六场景全量接入（组件底座 + S5 最深样板 + 五场景复制）

**为什么 S5 是最深样板（Q2 裁决后仍成立，且是五场景复制范式的验证场）**：① 数据最全——支线 B 是完整故事（客诉 DEMO-CC-001 → 批次 DEMO-LOT-002 → 工单 DEMO-WO-001 → 工序 30 ICT → 设备 DEMO-EQ-006 → 同批库存 2 批 3,952 件 → 8D 时间线）；② 平台有现成协同场景 `scenarios/customer_complaint_v2.yaml`（QA 牵头 → 四域并行 fan_out → 8D 工单 → 双 HITL：`hitl_d8_close` 质量总监/QA经理 + `hitl_complaint_reply` 业务经理），**是平台唯一的多智能体并行 DAG**，最能体现「各部门协同智能化」；③ 两个 HITL 槽位（`d8_close`/`complaint_reply`）已在 `GOVERNANCE_SLOTS`（`services/workflow.py` L132-137）中，**无需动全局治理面**；④ S5 屏已有 SVG 追溯图谱与定位动作（T06 已真机核对），改造是在既有骨架上「挂智能」，不是从零画图。
