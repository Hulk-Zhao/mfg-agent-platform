6. **阈值按「≥N 件」而不是「等于 N 件」**：演示库在制大单普遍 1.4 万件，

# 第三十棒：企微回调重放防护（2026-10-23）

> 依据：README 生产化清单——「企微回调重放防护：需补 timestamp 窗口验重 + nonce 缓存」。
> 原实现只验签名：同一份合法回调（含旧时间戳与重复 nonce）可被无限重放。

## 一、实现

### 修改

| 文件 | 改动 |
|---|---|
| `src/mfg_agents/v2/contracts/adapters/wecom.py` | 验签改用 `hmac.compare_digest`（常量时间）；新增 `_verify_signature`（只验签）、`_check_timestamp`（默认 ±300s）、`_consume_nonce`（Redis `SET NX EX` 优先 + 进程内 TTL 去重降级）、`_NonceGuard`；`verify_callback` 串起三道校验，`receive` 不再重复消费 nonce（避免合法链路被误判重放）；nonce 为空/超 128 字符直接拒绝；Redis key 带 appid 避免多应用碰撞 |
| `src/mfg_agents/common/config.py` | 新增 `IM_CALLBACK_MAX_SKEW_S`（默认 300；非法值回落默认） |
| `src/mfg_agents/v2/core/cache.py` | 新增 `set_if_absent`（Redis `SET NX EX` 原子写；不可用返回 None） |
| `.env.example` | 补企微回调凭据与重放窗口配置项 |
| `tests/v2/test_wecom_crypto.py` | 时间戳改为当前时间 + 唯一 nonce；新增 5 例：过期时间戳、未来时间戳、nonce 重放、Redis 不可用降级、先验后收不误杀 |
| `tests/v2/test_qa_crypto_vectors.py` | QA 观察项 OBS-1（重放同样通过）改为回归断言（重放必须拒绝）；篡改密文用例改用当前时间戳，确保测的是解密失败而非时间戳失败 |
| `tests/v2/qa_e2e_api_check.py` | GET/POST 改用当前时间戳与独立 nonce（否则会被新防护正确拒绝） |
| `src/mfg_agents/v2/demo/im_simulator.py` | 离线演示同样改用当前时间戳与 GET/POST 独立 nonce，避免演示脚本被重放防护正确拒绝 |
| `README.md` | 生产化清单标记已闭环（含真实租户 retry 的待确认项） |

## 二、验证结果

- 企微适配器（含 QA 独立向量）：**52 passed**；企微 + 健康探针相关：**76 passed / 2 skipped**。
- E2E 自查脚本：企微 GET 校验 / GET 伪造签名 403 / POST 回包 200 / 回包签名自验证 /
  回包含结论 / 回包含 HITL / POST 伪造签名 403 —— **企微相关全部通过**
  （脚本中「degraded 标记」一项按环境 LLM 可用性预期失败，与本轮无关）。
- **全量基线：2199 passed / 30 skipped / 0 failed（528.66s）**（上一轮 2194/30，
  本轮 +5 条重放/时间戳用例；QA 观察项 OBS-1 从"记录"转为回归断言）。

## 三、偏离与决策记录

1. **nonce 消费放在 `verify_callback`，不放在 `receive`**：API 的合法流程是
   「先 verify_callback 再 receive」；若 receive 再消费一次，会把正常请求误判为重放。
   `receive` 仍重复做签名与时间戳校验，防的是绕过 verify 的直接调用。
2. **Redis 优先、进程内降级**：多实例必须共享 nonce 状态，Redis `SET NX EX` 是原子的；
   Redis 未配置/故障时退回进程内 TTL 去重（单实例仍有效），不阻断业务。
3. **时间戳窗口默认 ±300s**：与企微文档的 5 分钟重试窗口同量级；nonce 去重窗口取 2 倍，
   保证窗口边界的时间戳不会留下 nonce 复用缝隙。
4. **不按 MsgId 去重**：MsgId 只有解密后可见，验证阶段拿不到；nonce 是签名三元组的一部分，
   在验签前即可判定，位置更前、成本更低。

## 四、遗留与下一步

1. **真实租户 retry 行为待确认**：企微超时重试是否复用同一 nonce 需实网验证；
   若复用，应改为「重复 nonce 返回幂等成功」而不是 403（避免丢消息）。
2. **nonce 去重未持久化**：Redis 不可用时进程重启会清空进程内表（窗口内极短）；
   生产应保证 Redis 可用。
3. **超时代签入口**：字段与展示已就绪，发起入口仍未开放。
4. **下一棒候选**：超时代签入口 / 生产只读账号联调 / 案例种子批量导入。

# 第三十一棒：案例种子导入连接复用（2026-10-23）

> 依据：第二十八棒遗留第 2 条——「MySQL 下逐条 upsert，种子量大时需批量写入」。
> 实测 221 例种子在 MySQL 上耗时 **41.06s**：`_conn()` 每次新建 pymysql 连接，
> 每例十余次建连，瓶颈在 TCP/握手而不是 SQL。

## 一、实现

### 修改

| 文件 | 改动 |
|---|---|
| `src/mfg_agents/v2/services/case_store.py` | 新增线程级 `_batch_conn()`：整段复用一条连接，结束时统一 `commit` / 异常 `rollback`；`_conn()` 检测到批量上下文时直接复用且不单独提交；`seed_from_json` 包进 `bulk_load()` + `_batch_conn()` |
| `tests/v2/test_case_seed_batch.py`（3 例） | 种子导入只建 1 条连接；批量成功提交；异常整体回滚 |
| `README.md` | 生产化清单补「种子导入连接复用 + 实测耗时」 |

## 二、验证结果

- **性能**：同机 MySQL 8.0.46，221 例种子 **41.06s → 1.70s（约 24 倍）**；
  落库计数与 SQLite 演示库一致（case 222 / acl 68 / evidence 2，含既有冒烟行）。
- 新增测试 3 例；案例种子 + 跨部门 + 契约回归 **53 passed**。
- **全量基线：2202 passed / 30 skipped / 0 failed（510.35s）**（上一轮 2199/30）。

## 三、偏离与决策记录

1. **连接复用而不是重写批量 SQL**：瓶颈是建连次数，不是单条 upsert；复用连接即可获得
   主要收益，业务 SQL 与幂等语义零改动。
2. **线程级而非实例级共享**：`CaseStore` 在 API 进程内是共享对象，若实例级缓存连接，
   其它线程会误入导入事务。用 `threading.local()` 隔离，导入线程之外仍各自连接。
3. **整批事务（原子）**：失败整体回滚，不再保留"前一半已导入"的半成品。种子可重放，
   下次重导即可；这比逐例提交更安全，代价是单事务稍大（221 例约 1.7s）。
4. **审计链不受影响**：`CaseAuditLog` 不进入批量上下文，仍保持独立连接 + 命名锁。

## 四、遗留与下一步

1. **更大种子量**：如果种子到数千级，可进一步改 `executemany` 多值 upsert；
   当前 221 例 1.7s，无需提前优化。
2. **生产只读账号联调**：仍是未完成项。
3. **超时代签入口**：字段与展示已就绪，发起入口仍未开放。
4. **下一棒候选**：超时代签入口 / 生产只读账号联调 / 行级数据范围。
