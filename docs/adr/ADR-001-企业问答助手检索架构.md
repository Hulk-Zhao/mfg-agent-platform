# ADR-001: 企业问答助手检索架构 —— FAQ 前置 + RAG 兜底，知识图谱暂缓

## Status
Proposed（待 Hulk 确认后转 Accepted）

## Context

- **业务**：企业内网问答助手（Business-Assistant 线），知识源 = 制度 / 流程 / IT 支持文档，用户 = 多岗位员工，答案必须可溯源、受权限控制。
- **已有参考实现**：本地 `D:/EDURAG/Itcast_qa_system`（EduRAG V7.5）已跑通两层链路：
  - 前置层 `mysql_qa/retrieval/bm25_search.py`：BM25 全量打分 + softmax 归一，阈值 0.85，未命中回落 RAG；Redis 缓存语料与答案。
  - 兜底层 `rag_qa/`：Milvus 向量检索 + BERT 二分类（通用知识/专业咨询）+ LLM（DashScope）四策略选择。
- **待决策问题**：是否以知识图谱作为检索底座，取代 FAQ 前置 + RAG 兜底的两层结构。
- **约束**：本地部署（FastAPI + MySQL + Milvus + Redis），小团队维护，无专职图谱工程师；Milvus 尚在 2.4.4 升级中。

## Decision

采用 **L0/L1/L2 三层检索 + 统一答案契约 + 晋升管线**。知识图谱**不进入本期底座**，仅作为未来 L3 通道的预留扩展点。

| 选项 | 结论 | 理由 |
|---|---|---|
| A. 知识图谱底座 | 否决（本期） | 本体设计 + 实体抽取 + 持续 curation 是周~月级成本；企业问答中多跳关系类问题占比小；本体错误纠正昂贵，不可逆 |
| B. FAQ 前置 + RAG 兜底 | **采纳** | 复用全部现有中间件；重复问题（企业问答大头）毫秒级命中；可逆，数天可建 |
| C. 纯 RAG | 否决 | 重复问题反复烧 LLM 延迟与成本；答案无法固化为权威口径 |
| D. 结构化库 + Text-to-SQL | 按需补充通道 | 参数/聚合类问题上 BM25 与向量检索都无能；比 KG 便宜一个数量级 |

目标链路：

```
用户问题 → L0 Redis（键含权限范围）→ L1 FAQ 语义匹配（绑定源文档版本）
→ L2 RAG（ACL 过滤 + 引用）→ 统一答案契约
晋升管线：RAG 回答 → 点赞/管理员确认 → FAQ 草稿 → 发布回 L1
未来 L3：知识图谱（仅当下方判据满足时启用），接入同一答案契约，零重构
```

统一答案契约字段：`answer` / `evidence` / `confidence` / `sources` / `channel` / `audit`。

## Consequences

**变得容易**
- 重复问题（制度、流程、IT 支持类占企业问答七成以上）毫秒级命中，LLM 调用量与延迟大幅下降。
- 全部复用现有 FastAPI / MySQL / Milvus / Redis，不新增中间件与故障面。
- FAQ 命中率成为可运营指标；晋升管线让系统越用越快。
- 知识图谱以后作为独立通道插入，答案契约不变，无重构成本。

**变得困难 / 新增负担**
- 前置阈值必须用评估集定标，不能拍脑袋（EduRAG 现有 0.85 不可信，见风险 1）。
- 需维护 FAQ 与源文档的版本绑定、缓存失效逻辑。
- 多跳关系类问题本期只能靠 RAG 兜底；答不好的部分靠日志度量暴露，而不是假装不存在。

**风险与缓解（基于 EduRAG 代码审查）**

| # | 风险（代码位置） | 缓解 |
|---|---|---|
| 1 | softmax(BM25) 阈值 0.85 不是校准过的置信度；语料增长后分数分布漂移，同问不同分（`bm25_search.py::search`） | 前置改双路召回（BM25 + embedding 余弦），用 top1/top2 的 margin 做阈值，用 EduRAG 第⑤章评估集定标 |
| 2 | Redis 答案缓存无失效、无版本绑定；FAQ/文档更新后仍返回旧答案 | 缓存键绑 FAQ id + 文档版本；写 FAQ 时主动失效；缓存可只存命中判定不存答案正文 |
| 3 | FAQ 层不学习，RAG 答得对也无法沉淀 | 晋升管线：点赞/管理员确认 → FAQ 草稿 → 发布；每月 review 晋升通过率 |
| 4 | 企业 ACL 完全缺失；缓存跨用户共享 = 越权泄露变体（A 的涉密答案被 B 命中） | 全通道权限过滤；缓存键绑权限上下文；未登记文档 fail-closed（复用 mfg 项目 data_scope 的既有纪律） |
| 5 | 每次查询多一次 LLM 策略选择调用，延迟与成本双输（`strategy_selector.py`） | 仅对 L1 未命中且 L2 低置信的查询启用策略选择 |

**知识图谱启用判据（度量驱动，三者须同时满足）**
1. 运行日志中多跳关系类查询占比 ≥ 15%，且这些查询 RAG 置信度持续偏低；
2. 领域关系密集且稳定（如 供应商-零件-产品、故障-症状-原因）；
3. 有明确的本体维护责任人（具名，不是"我们会抽时间"）。

不满足任一条，继续 FAQ + RAG。

## 备注

以上风险定位基于 EduRAG 基础版代码；若讲义 6.2「优化版」已调整阈值/失效策略，以评估集实测结果为准，本 ADR 的结论不受影响（改的是实现细节，不是选型）。
