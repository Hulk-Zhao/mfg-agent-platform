## 7. 与规格/代码现实的冲突记录（以代码现实为准）

1. **`inventory` 不新增第 3 行**（规格 §4.3 建议加 `(3,'A型号','上海成品仓',300,300)`）：
   现实约束——`tests/v2/test_text2sql.py::test_detail_channel_generates_and_audits` 断言
   `SELECT COUNT(*) FROM inventory` 结果 `== 2`；加行会破坏既有 QA 测试。
   ➜ **处理**：不加库存行；S4 的 ATP 用既有 A型号库存（1200-800=400）与订单（2000+1500）计算，
   故事完整（缺口 3100pcs）。并新增 `test_data_redline_inventory_count_unchanged` 锁死。
2. **设备取证经 `equipment_warn` wrapper 取条件键**（规格 §4.4 写 `agent=equipment`）：
   现实约束——现有 `equipment` handler 属冻结项，不能改其 payload 增加 `has_alarm`。
   ➜ **处理**：新增 key `equipment_warn`，内部**调用**冻结的 `equipment` handler 并补
   `has_alarm` 布尔键（复用而非修改），YAML 使用 `agent: equipment_warn`。
3. **provenance 聚合改从 SharedContext 采集**（`orchestrator._collect_provenance`）：
   现实缺陷——原实现遍历 `dag.domains`（按域 last-write-wins），多分支同域时（S4 六个分支
   中 5 个属 `supply_chain`）会丢失部分分支的 SQL provenance。
   ➜ **处理**：改为遍历 `SharedContext` 的 `provenance` 记录历史（只增不改），
   捕获**每个** handler 的 provenance；line_stop 行为等价（各分支域唯一）。
4. **8D 不建表**（规格 §8.4 U1）：D1-D8 由 `qa_lead` 规则模板确定性合成，由 `capa_flow`
   工单 context 承载。**已在本文与 README 标注为演示简化**；"生产需持久化 D1-D8 步骤"
   列入下方生产化清单。
