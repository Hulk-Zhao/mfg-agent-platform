执行摘要Executive Summary

本方案回答一个问题：如何从现有可运行原型，演进为覆盖 16 个部门的制造业多智能体协同办公平台。结论先行：不做推倒重来，做演进式架构；不铺 16 个 Agent，做 1+1+4+N 拓扑；不让 LLM 碰确定性流程，用工作流引擎承载协同。

架构一句话：以 IM 机器人为统一入口、智能总控为唯一编排枢纽，16 个部门按价值流聚为 5 大业务域智能体组，复用 Text2SQL / RAG / 工作流 / 预警 / 报表 / SPC 六类无状态能力服务，数据经 ODS→DWD→指标库分层治理，全栈私有化部署，关键决策全部人在环路。

四个核心判断

  • 多智能体是手段不是目的：16 部门 ≠ 16 Agent。进度对齐中大部分动作是确定性流程（状态推进、审批、通知、升级），走工作流引擎；LLM 只做理解、推理、分析、生成。
  • 数据质量决定平台上限：源头数据不准，智能体只会更快产出错误答案。"数据与集成盘点"列为阶段 0，先于任何 Agent 开发。
  • 制造业数据不出厂：BOM、工艺参数、供应商价格、客户信息为核心资产，全栈私有化 + 本地模型优先（Ollama qwen 系列），外部 API 仅限脱敏后非敏感场景。
  • 演进不重写：V1 原型已验证 LangGraph fan-out/fan-in 编排、Text2SQL 只读模式、RAG+LLM 结构化输出三大模式——这是资产；四个硬编码（场景/路由/状态/Schema）是债——这是改造点。

项目基线事实

  • 已有原型：mfg-agent-platform，LangGraph 编排 8 Agent、5 场景（停线应急/来料异常/客户投诉/出货风险/设备预警）、8 张模拟表、Text2SQL + RAG、Streamlit + FastAPI(SSE)、Docker Compose。
  • 定位是事中应急查询型：用户提问 → 路由 → 并行取证 → 报告。
  • 缺口：IM 入口、主动预警、工作流引擎、审批、用户权限、定时报告、跨部门进度看板；git 尚无任何提交。
  • 市场结论：买不到开放的 16 部门协同平台（右上象限仅绑定自家生态的 ERP 大厂），自建空间成立——但底座全部复用开源与现有 IM，只自建"协同语义 + 质量分析 + 权限脱敏"三件核心资产。

  6. "工作流引擎 + Agent"混合架构成为工程共识：CoMi 将问数引擎/流程引擎/知识中台分层，钉钉设"过程监控 + 拔电"——直接验证本平台"确定性走流程、智能走 Agent"的架构决策。致远互联

三、业务架构Business Architecture

业务架构的核心决策是按价值流聚类而非按部门镜像划分智能体——后者会导致 agent sprawl（智能体泛滥），这是此类平台第一大死因。16 个部门聚为 5 大业务域，域内共享主数据与协同频率，域间走事件契约解耦。

场景详设 A：S1 停线应急协同（从"人等问"到"事件自动触发"）

  • 参与分工：制造 Agent 确认停线事实 → fan-out 并行：质量 Agent（不良分布/IPQC）、供应链 Agent（来料批次/供应商状态）、设备 Agent（告警/参数）→ 总控汇总进 SharedContext → FA 分析（RAG+LLM：评级/根因/复线 ETA）→ 工作流引擎执行影响评估（通知计划/物控/业务——这是 V1 完全没有的确定性联动）。
  • 触发方式：① 员工 IM 提问（V1 方式）；② 新增 MES 停线事件经事件总线自动触发，无需人等问。
  • 输出物：内部简报（评级/根因/ETA/证据链）、对客脱敏报告（V1 禁词表机制保留）、影响评估工单（计划调整/物料替代/对客沟通任务）。
  • 异常与升级：任一域 30s 超时标记 degraded 继续；FA 置信度低→人工分析任务升级 PQE；停线>2h→升级制造经理+生产副总；复线动作必须制造现场负责人 IM 卡片确认（HITL）；对客 ETA 必须业务确认后才允许输出对外话术。
图 3 · S1 停线应急协同流程（红色 = HITL 人工确认点，贯穿全程可审计）

场景详设 B：S5 缺料预警——从"人找 Agent"到"Agent 找人"的主动型样板

  • 参与分工：物控 Agent 定时扫描（安全库存/在途/在制消耗速率）→ 预测缺口 → fan-out 联动：计划 Agent（可否改排）、采购 Agent（催交/替代）、制造 Agent（影响线体/工时）、业务 Agent（影响订单/客户）→ 工作流引擎分派处置 → 跟踪闭环。
  • 触发方式：APScheduler 每 4h 扫描（注册查询模式，非自由生成 SQL）→ 缺口事件 → 多域并行评估 → 工单分派 → 每日 IM 播报进展。本场景没有用户提问触发——这是平台从工具进化为基础设施的关键转变。
  • 异常与升级：影响停线风险 <48h → P1 立即 IM 通知计划+采购+制造经理；加急采购金额>阈值 → 采购总监 HITL；误报率监控（关单时标注"未实际发生"回流优化阈值）。

5.1 框架选型：LangGraph 深化（已决策）

维度LangGraph 继续深化（推荐）引入 Dify 做低代码编排

六、演进策略Evolution Strategy

V1 最大的资产不是 8 个 Agent 代码，而是三个经过验证的技术模式：LangGraph fan-out/fan-in 编排、Text2SQL 只读安全模式、RAG+LLM 结构化输出。最大的债是四个硬编码：场景硬编码、路由硬编码、状态平铺、Schema 写死。演进主线：把硬编码的场景知识抽成声明式配置，把单体状态拆成分域状态，把手工编排的 API 收敛回 LangGraph 图。

6.1 迁移兼容策略（保护演示能力，不打破旧世界）

  1. 分支：V1 代码在 main 保持可运行可演示；演进在 v2-dev 分支，按里程碑合回。
  2. 场景等价：scenarios/line_stop_v2.yaml 必须通过 V1 的 5 场景回归用例（tests/test_e2e.py 现有断言不改，只扩不缩）。
  3. 状态兼容：SharedContext.get("oee_data") 仍能读到旧字段名——老字段作为 domain-scoped 别名保留映射表。
  4. 事件兼容：EventBus 发布的事件 type 枚举与 V1 前端完全一致，Streamlit 前端零改动先用起来。
  5. 数据兼容：8 张模拟表保留为 dev fixture（DB_PROFILE=dev）；真实系统接入走 DB_PROFILE=prod + 数据源注册。
  6. 契约测试先行：每重构一个模块，先在 tests/ 补契约测试再动代码（尤其 sql_tools 的只读保证——安全边界，必须覆盖 DDL/DML 注入用例）。
  7. 影子期：新旧路由并行跑，比对不一致记录到 route_diff 表，人工抽检后切流。

T05入口与协同闭环IM 网关（企微回调+消息卡片）+ 工作流引擎（状态机+审批+升级）+ 缺料预警 + api.py 统一编排入口（保留旧 SSE 端点）T02, T03, T04
阶段 1 里程碑：M1（W1-2）基础设施 → M2（W3-4）场景注册表与动态路由 → M3（W5-7）供应链域组 + Text2SQL 服务化 → M4（W8-9）企微机器人 + 缺料预警工作流 → M5（W10-12）试点运营、影子切流、旧端点下线、复盘。

八、风险与批判性分析Risks & Critical Review

8.1 不该用多智能体/LLM 的需求（走确定性工作流）

需求为什么不该用 LLM正确实现
报销/请假/采购申请审批流规则完全确定（金额阈值、组织架构、余额校验）工作流引擎 + RBAC
ECN/BOM 变更流转状态机 + 权限矩阵确定工作流引擎；Agent 仅做影响分析建议
库存扣减/出入库过账强一致事务，错一次就是账实不符事务型业务系统（WMS/ERP）
CPK/SPC 数值计算与控制图判异确定性统计算法（8 大判异准则），LLM 算数不可靠Python 统计库计算；LLM 只解释"这意味着什么"
SQL 执行与结果集返回执行层必须确定性白名单校验后由引擎执行；LLM 只生成 SQL 草稿
权限校验与数据隔离安全边界不能概率化RBAC 中间件，Agent 无特权
定时任务触发、报告分发、消息通知调度与投递是确定性基础设施调度器 + 消息通道
排产（APS）优化约束求解问题，LLM 不擅长精确优化APS 算法；Agent 做参数解释、方案对比说明
停机/停产等物理动作执行安全关键，必须人确认人工审批 + 系统指令

8.2 风险清单与缓解

#风险概率/影响缓解措施
R1Agent sprawl：16 部门各自要 Agent，数量膨胀失控高/高1+1+4+N 拓扑：路由闭集 5 域组；新增 Agent 需过架构评审（必须有新数据域或新决策闭环的理由）
R2数据质量差：源头脏数据使智能输出"精确的垃圾"高/高ODS 质量标记 + DWD 清洗门禁；指标库唯一口径；无 DWD 的域不开放自由 Text2SQL；数字结论强制 provenance
R3集成成本占比超预期（60-70%）高/高阶段 0 只打通 1 个系统；MCP 标准封装；RPA 兜底但有边界；集成工作量单独跟踪
R4LLM 幻觉/错误导致错误决策（编造在途数量、错误根因）中/高统计量代码计算；数字必须溯源 SQL 行；AST 审核+结果校验；关键决策 HITL；红队测试用例进评测集
R5LLM 成本与延迟：大模型全量调用不可持续中/中L0/L1/L2 分级；本地小模型兜底；规则快路径；结果缓存；token 成本周报
R6安全合规：数据不出厂红线被突破中/高涉敏推理强制本地 LLM；外部 API 仅限脱敏后非敏场景；RBAC 双轨 + 行级过滤下推；渗透测试
R7组织变革与采纳：部门墙、不信任、沦为演示玩具高/高从 3 个高频痛点切入；试点部门共创；HITL 设计给人掌控感；周活/点踩率/人工改写率周会跟踪
R8缺乏评估体系：无法证明价值，项目烂尾中/高阶段 0 即建评测集（≥50 条，CI 门禁）；价值度量对齐业务语言（停线时长、OTD、8D 周期）
R9供应商锁定：LLM/IM/框架绑架中/中LLM 工厂抽象；IM 适配层三平台同接口；MCP 标准封装；场景 YAML 与编排框架解耦
R10Text2SQL 准确率天花板：真实 ERP 复杂语义超模型能力高/中指标库优先；注册查询覆盖高频；Text2SQL 只做明细探查；超范围人工兜底；Few-shot 持续回流

8.3 伪需求/低价值场景识别

候选需求判定理由与处置
"全自动无人处置"（自动停产、自动改排产、自动处罚供应商）伪需求责任主体不清、错误成本极高；定位"Agent 建议 + 人一键批准"，M4 后再评估窄场景
"企业万事通"大而全知识助手低价值无场景约束的问答使用率快速衰减；绑定场景（只做质量/制度/案例三类域）
自然语言直接生成财务凭证/过账伪需求财务合规不允许概率性生成；用表单+规则，Agent 只做辅助填写
数字人/虚拟形象/语音炫技低价值与两大目标无关，验收时明确不做
全量设备预测性维护（AI 模型）暂缓传感器实时数据不具备；先用日志规则预警，数据就绪后再上模型
"一句话生成任意复杂报表"的完全自由 BI低价值（过度承诺）自由问数准确率随复杂度指数下降；做"受控问数"：限定指标域 + 模板化 + 置信度提示
用多智能体做简单单表查询过度设计单表确定性查询走模板/规则直查更快更准，多 Agent 只用于跨域并行取证

8.4 三条不可妥协的架构纪律

1. LLM 不碰确定性流程：审批、通知、升级、状态流转永远走工作流引擎——这是可审计、可重放、可举证的前提；LLM 只出现在需要理解、推理、生成的地方，且产出必须可溯源。
2. 数据质量先于智能能力：没有 DWD 和指标库的域，不开放自由 Text2SQL；数字结论必须带 provenance。宁可"查不到 + 人工兜底"，不可"编得出 + 没人发现"。
3. 演进不重写，场景不铺开：5 个 V1 场景先等价迁移进注册表，3 个高频场景先进试点，16 个部门按路线图逐域推进。

九、待决策清单Open Decisions

#待决策事项影响当前默认假设
