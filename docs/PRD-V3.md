## 0. 一句话

**V2 让系统"能把事办完"，V3 要让系统"能证明这件事是按规定办的"——补齐治理层（权限/会签/审计）、受控知识资产（质量文件版本受控）、数据边界（部门/产线/客户隔离）与协作原生化四块地基，使得每一次跨部门决策都可追溯、可审计、可复现。**

### 为什么是这四块（3 条理由）

**理由 1：V2 的 5 个场景都是"一次性的"**
停线处置完，结论留在 IM 聊天记录里；8D 关闭后，报告存在 `outputs` 里再没人打开。**同一类问题第二次发生时，系统没有任何记忆**。分两种缺失：① 标准类文件（SOP/检验标准/图纸）**不是受控资产**——没有编号、没有版本、没有生效日期、没有批准人签名（客户质量体系审核 ISO 9001 8.5.6 / IATF 16949 7.5.3 看的就是这个）；② 过程记录（8D）**不是可复用的知识资产**——没有结构化抽取、检索不到、复用不了。**这两类缺失用两种不同的容器解决（受控文档 vs 知识资产），不能混为一谈**（见 §0.5 裁定 2）。

**理由 2：治理层是"平台化"的前置条件，不是可选项**
Huly 的 QMS 产品（TraceX）没有写一行业务模型代码——它把通用的「受控对象 + 状态机 + 会签 + 空间权限」配起来，就交付了一个符合 ISO 13485 4.2.4 的质量系统（见对标分析 §7 结论 3）。**反过来说：如果没有这层通用治理，每加一个合规场景就要重写一遍审批流程，场景数一多必然失控。** 我们目前 5 个场景已经有 7 个 HITL 槽位、21 条权限，再往上加会开始出现"每个场景的审批逻辑长得不一样"的债务。

Agent 必须以 `actor_type='agent'` 显式落库，且不得持有任何 `*.approve` 权限。V3 必须让"Agent 的每一次写入"和"人的每一次签字"一样留痕。

## 0.5 主理人裁定（2026-10-16，五项决策 + 一项补充）

> 本节为**决策记录**，效力高于本 PRD 其余章节的"建议"。凡与本节冲突的表述，以本节为准。

### 裁定 1：治理层硬门禁 —— 设，但门禁范围精确到三项

**裁定**：阶段一设置硬门禁，但**只要求以下三项完成即可放行**，不要求"完整审计体系"建设完毕：

| # | 门禁项 | 判定标准 |
|---|---|---|
| G1 | **会签门控** | 含 `select_action` 时**动态生成**会签要求（不能在建单时把全部动作的 cosign 取并集固定）；会签未齐时 approve 必须被拒 |
| G2 | **后端权限校验（fail-closed）** | 每个写操作在 handler 前校验；未识别角色/权限一律拒绝；不依赖前端传的 `role` |
| G3 | **审计留痕** | signoff 与 approval **落库且可追溯**（能按 `task_uid` 还原完整决策链），不要求"审计体系"级别的报表/导出/归档 |

**理由**：受控文档最大的合规风险是"批准可以被绕过"。这三项恰好堵住"绕过"的三条路径——少签、越权签、无痕签。把门禁卡在"堵漏"而非"完备"，是为了不让治理层拖住受控文档的首发。

### 裁定 2：首批强制受控文件 —— 3 类，8D 报告**不纳入**

**裁定**：阶段一强制受控范围 = **SOP / 检验标准 / 图纸**。**8D 报告不进受控文档体系**，改走「知识资产」路径（阶段二，见 S9）。

**理由**：8D 是**过程记录**，不是受控文件。受控文件的本质是"约束行为的标准"（你可以拿 SOP 要求人怎么做），8D 的本质是"对已发生事件的追溯"。强行把 8D 纳入受控，会带来两个后果：① 8D 闭环被"编制→审阅→会签→终批→生效"五个环节拖慢一个量级，而 8D 的价值恰恰在于快；② 8D 需要频繁补充（客户追问、验证结果回填），而受控文件的铁律是"错了只能发新版"。**用受控的容器装过程的记录，是两个概念错配。**

**8D 的正确归置**：`hitl.d8_close` 终批通过后，作为**知识资产**落库（结构化抽取"现象/根因/对策"），可检索、可复用、可被引用，但**不受版本控制、不需要生效日期、不作废**。

### 裁定 3：PDF 导出 —— 不用 WeasyPrint，改「浏览器原生打印样式 + Playwright 服务端渲染」

**裁定**：
- 前端用 `@media print` 定义分页、页眉页脚、隐藏非打印元素（零新增依赖）；
- 服务端用 **Playwright** 加载页面并 `page.pdf()` 出 PDF（项目内已有 Playwright，QA 已在用，**零新增系统级依赖**）。

**理由**（推翻本 PRD 初稿的 WeasyPrint 建议）：WeasyPrint 依赖系统 cairo/pango，在 Windows 上部署痛（客户现场多为 Windows Server）；我们的前端本就是 HTML/CSS，`@media print` 是浏览器的原生能力，成本近乎为零；Playwright 已在项目依赖里，服务端出 PDF 不需要再引入 Cairo/Pango/字体包。**一个选型的成败往往不在功能而在"客户机能不能装上"。**

**约束**：`@media print` 与 `page.pdf()` 必须产出**同一份版式**（同一 CSS，不写两套）；验收时以服务端 PDF 为准，前端打印为副产品。

### 裁定 4：超时代签 —— 允许，但受四条硬约束

**裁定**：允许超时代签，但必须同时满足：

| # | 硬约束 | 实现要求 |
|---|---|---|
| C1 | **强制填写理由** | 理由字段不可空（空则 400）；理由文本进审计原文，不可编辑 |
| C2 | **independent 审计标记** | history 中标记 `overdue_signoff`；看板**单独统计**该类签名，不与正常签名混算 |
| C3 | **必须由上级角色执行** | 仅 `quality_director` / `gm` 可代签；**同级不可代签**（如 SQE 不能代 PQE） |
| C4 | **必须留痕"代的是谁的签"** | signoff/approval 记录必须带 `on_behalf_of: <被代的 role key>`；history 表述为 `代签（原应签：SQE，代签人角色：质量总监）`。**`overdue_signoff: true` 与 `on_behalf_of` 两个字段必须同时出现，缺一不可** |

**理由**：现场一定会绕过系统（用微信+口头），堵死等于数据失真——数据失真比"有瑕疵的留痕"更糟。但代签必须"贵"：填理由有心理成本、`overdue_signoff` 标记有声誉成本、只能用上级角色有权力成本、留痕"代了谁"有问责成本。**四条叠加才能让代签成为例外而非常态。**

**C3 的边界说明（主理人裁定）**：不引入 `reports_to` 组织层级（理由见 §6.5 K6）。因此 C3 的实现含义是"**任何 `gm` / `quality_director` 可代任何角色的签**"——这在合规上不是漏洞而是授权边界：ISO 审核问的是"谁有权代签 + 有没有理由 + 能不能追溯"，不是"是否严格直接上级"。

**C4 的必要性**：C3 放宽了"谁"（不校验直接上级），就必须收紧"代了谁"（`on_behalf_of` 必填）。**两者是一对补偿关系——放宽一层，必须补一层留痕，否则审计链断裂。**

**本轮实施范围（主理人裁定）**：**本轮不实现代签入口**。本轮只交付 ① 字段位（`on_behalf_of: null` + `overdue_signoff: false` + `actor_kind` 已就位，后续接入代签无需改结构）② fail-closed 底线（`test_cosign_cannot_spoof_role`：actor=张三、`role="qa"`、`user_ctx.roles=["warehouse"]` → 403，锁定"不存在任何伪装/绕过入口"）。**C1-C3 与 C4 的四组反例测试顺延到代签轮**，届时按上表全测。

### 裁定 5：scope 粒度 —— 阶段二 `dept` + `line`，`customer` / `project` 放阶段三

**裁定**：按产品建议执行。**但必须在风险清单中显式写明**（见 §5 R10）：阶段二客诉数据**仅靠角色级脱敏兜底，未做客户级数据隔离**。

**理由**：`dept` + `line` 覆盖停线与来料两个高频场景；`customer` / `project` 涉及跨客户数据，需要更完整的授权模型。但"暂时不做"不等于"不用声明"——**必须在文档层面留下这条已知缺陷，避免上线后被合规审计当作隐瞒**。

### 补充裁定（优先级高于本 PRD 原第 3 条结论）：审批即待办，且待办必须到人

**裁定**：阶段一验收标准**必须包含**以下两条，并作为"治理层是否算完成"的判断依据之一：

| # | 要求 | 判定标准 |
|---|---|---|
| G4 | **HITL 待办能推送到 IM** | 企业微信卡片送达，卡片上可看到待签事项与当前签名进度 |
| G5 | **待办按人过滤** | 提供"我的待办"（按当前 `user_ctx` 的角色集合过滤），而非"全部待办" |

**理由**：**制造业的现实是审批人不在系统里，审批发生在微信里。** 一条推不到人的待办，等于没有待办；一个只能看"全部待办"的列表，在 16 个部门 7 个槽位下等于不可用。这条比 Permission 模型的抽象程度更直接决定系统会不会被真实使用——因此优先级高于"Permission 对象化"这类结构性改进。

**与 G1-G3 的关系**：G1-G3 解决"批准不能绕过"，G4-G5 解决"批准真的会发生"。**六项（G1-G6，G4/G5 视为一组）全部满足，治理层才算完成。**

### 裁定 6：G6 会签独立性（SoD）—— 与 G1-G5 同权

> **这条不是理论风险，是穿透测试抓到的真实缺陷**：引擎级测试中，同一 `user_id` 连续以 `pqe` / `sales` / `qa` 三个角色会签，结果 **3/3 满足、工单可放行**，signoffs 里三行都是同一个人的名字——**一个人独自完成了"三方会签"**。
>
> 根源之一是演示岗位映射把 `pqe` 身份做成了 `sqe+pqe+qa`（理由是"便于单人演示三方会签"）。**这是把演示便利凌驾于业务真实性之上**，必须在产品层面禁止，而不是靠测试兜。

**裁定：会签独立性是治理层的硬约束，与 G1-G5 同权。**

| # | 约束 | 判定标准 |
|---|---|---|
| S1 | **一人一签** | 同一 `user_id` 在同一工单内**只能会签一次**（不论角色）。跨角色重复会签 → **409 `SignoffConflict`** |
| S2 | **判定依据是 `user_id`，不是姓名** | 重名、改名、前端伪造姓名都不影响判定；不得用 `actor`/`actor_name`/`role_name` 做唯一性依据 |
| S3 | **受治理工单必须携带 `user_id`** | 缺失 `user_id` 的会签请求 → **403 `PermissionDenied`**，不得降级为"按姓名去重"或"默认放行"。<br/>**为什么是 403 而非 400**：缺 `user_id` 不是"请求格式错误"，而是**"身份不足以判定权限"**——它与"角色无该权限"同属授权失败，前端有统一处理（403 → "当前岗位无权限" + 具体需谁）。用 400 会让前端走到"请求参数错误"分支，提示会误导用户 |

**允许的例外（唯一一条）**：**会签人之一可以同时终批**。质量总监既做会签又做终批是正常业务（他既是质量侧会签人，又是终批人），这种情况只消耗一次签名。
**不允许**：同一 `user_id` 以**两个不同会签角色**签署（这是本缺陷的形态）。

**发起人边界（产品判断，工程师按此实现）**：

> **发起人可以同时是会签人——但只能签一次。**

理由与边界：
- **允许**：SQE 发起处置，同时他确实兼任 PQE 负责人，他可以在 `pqe` 会签位上签一次。现实中兼岗存在，一律禁止会让流程凑不齐。
- **禁止**：同一人**既以发起人身份选动作、又以两个不同会签角色签署**。发起是"提案"，会签是"背书"，一个人可以在两个身份上各出现一次，但不能在同一层身份上重复占位。
- **实现口径**：唯一性约束作用域是 `(task_uid, user_id, verb='cosign')`——即"同一人在同一工单上的会签行为只能有一条"。发起（`propose`）不占会签名额，因此"发起 + 一次会签"是两条不同 verb 的记录，**不冲突**。

**验收要求（必须正反例成对存在）**：
1. 反例：同一 `user_id` 以第二角色会签 → **409**。
2. 反例：会签请求缺 `user_id` → **403 `PermissionDenied`**（授权失败语义，非参数错误）。
3. **正例（必须有）**：两个**不同** `user_id` 正常完成会签、工单可放行。
   > 第 3 条是为了防止"把会签整体锁死"被误判为"实现正确"——只会拒绝不会通过的实现同样不合格。

**为什么放在治理层而不是演示层**：演示便利（单人跑通三方会签）与治理真实性（三方会签必须是三个人）是**互斥**的。一旦允许"一人多签"，`audit_log` 里的会签记录就失去证明力，受控文档的"批准人签名"也失去体系意义。**演示环境应该用三个不同账号，而不是让一个人扮演三个人。**

## 1. V3 新增能力域（4 个，按优先级）

### 能力域 ① 治理层：权限 / 会签 / 审计（P0，**阶段一已交付**）

**目标**
任何跨部门决策（7 个 HITL 槽位）都必须满足：① 发起人有 propose 权限；② 会签人齐备（缺一不可）；③ 终批人有 approve 权限；④ 全过程有不可篡改的审计轨迹。**任一条不满足 → 拒绝（fail-closed），不做"默认放行"。**

**关键能力**

| 能力 | 说明 | 现状 |
|---|---|---|
| 声明式权限目录 | 21 条 `hitl.<slot>.<verb>` 权限 + 15 角色 + 别名归一化 | ✅ 已交付（`v2/data/permissions.yaml`、`v2/contracts/permissions.py`） |
| 槽位白名单 | 每个 HITL 槽位显式声明"该槽位支持哪些权限"（对标 Huly `availablePermissions`） | ✅ 已交付：7 个 slot × 3 条已填；校验"未声明 / 目录里没有 / 不归属本槽位"三类错误 |

| 会签门控（动态生成） | `select_action` 按**选中动作**生成 propose/cosign 要求；`signoff_status()` 判定是否齐备 | ✅ 已交付：建单时 `required_signoffs == []`；测试 `test_different_actions_have_different_signoffs` 断言"退货→仅采购 / 挑选全检→生产+采购 / 特采→PQE+业务+QA"，证明不是取并集 |

### 能力域 ② 受控文档与知识资产（P0）

**目标**
把 SOP、检验标准、图纸、ECN 从"一次性产物"变成**有编号、有版本、有生效日期、有批准人、可追溯**的受控资产。一份文件只有处于 `effective` 状态才能被引用为"标准"，旧版本自动转 `obsolete` 但永久可查。

> **裁定 2 边界（见 §0.5）**：**8D 报告不纳入受控文档体系。** 本能力域只覆盖"约束行为的标准类文件"（SOP / 检验标准 / 图纸）与"变更依据类文件"（ECN）。8D 是过程记录，走 S9 的知识资产路径（可检索/可复用，不受版本控制、不需生效日期、不作废）。

**关键能力**

| 能力 | 说明 | 对应 Huly 设计 |
|---|---|---|
| 文档主数据 | `doc_code`（如 `SOP-QA-014`）+ 标题 + 类别 + 归属部门 | `TDocument.code/prefix/seqNumber` |
| 双版本号 | `major.minor`；major = 换版（需重批），minor = 修订（需会签） | `TDocument.major/minor` |
| 双状态 | `lifecycle_state`（draft/effective/archived/obsolete）+ `review_state`（inReview/reviewed/inApproval/approved/rejected/toReview） | `DocumentState` / `ControlledDocumentState` |
| 四组角色 | 编制人 / 审阅人 / 批准人 / 外部批准人（客户或监管） | `coAuthors/reviewers/approvers/externalApprovers` |
| 变更控制 | ECN 实体：原因 + 影响分析 + **受影响文件清单** | `TChangeControl` |

| 版本快照 | 每次批准生成不可变快照（内容 ref + 状态 + 批准人 + 时间） | `DocumentSnapshot` |
| 全文检索 | SOP/图纸/ECN/8D 全文可搜（SQLite FTS5，8D 走知识资产索引） | `fulltext` + `rekoni` |
| PDF 导出 | 受控文件与 ECN 导出带编号/版本/生效日期的 PDF；**前端 `@media print` + 服务端 Playwright `page.pdf()`，同一份 CSS**（裁定 3） | `print` 服务 |

**依赖的现有资产**

**验收标准**
1. 创建 SOP 时自动生成编号，格式 `SOP-<dept>-<seq>`，seq 不复用（删除后也不复用）。
2. 提交审阅 → 审阅中 → 批准中 → 已生效，四步状态流转可查；**非法流转被拒绝**（如 `effective → inReview` 直接 400）。

## 3. 能力与现状的差距表

| 能力 | V2 能做 | V2 不能做 | 缺什么（V3 要补） |
|---|---|---|---|
| **权限判定** | 21 条权限、15 角色、别名归一化、fail-closed | 槽位白名单未填；无对象级/字段级权限 | 补 `slots[].available_permissions`；可选 `resource`/`attribute_scope` |

| **协作** | SSE 推事件；IM 推卡片 | 卡片不能反向操作；报告是只读的 | IM 双向会签 + 段落认领 + 批注 resolve |
| **导出** | 前端展示 Markdown | 无 PDF；无页眉页脚版本信息 | **`@media print` + Playwright `page.pdf()`（裁定 3，不用 WeasyPrint）** |
| **Agent 治理** | Agent 在编排里跑，`on_error=degrade` | Agent 写入是否越权不可查 | `actor_type` + Agent 不得持 approve 权限的断言 |

## 5. 风险与前置条件

| # | 风险 / 前置条件 | 影响 | 应对 |
|---|---|---|---|
| **R1** | **治理层未完成则 V3 其余全部不成立**（硬依赖） | 会签不准、审计不全，受控文档的"批准"就没有法律/体系意义；数据边界也无法校验 | 阶段一退出条件作为**硬门禁**，不达标不进阶段二。这条不接受"先上线再补" |
| **R2** | **会签卡死**：某个会签方长期不处理，流程永久停在 `waiting_hitl` | 现场会绕过系统，用微信+口头，系统被架空 | 必须同时交付：`escalate`（已存在 `workflow.py:184`）+ SLA 超时自动升级（`check_sla` 已有）+ **超时 N 小时后允许"代签 + 理由 + 审计留痕"** 的旁路 |
| **R3** | **scope 加漏导致越权读取**，尤其 Text2SQL 生成的动态 SQL | 一个客户看到另一个客户的客诉 = 商业事故 | ① 只给三类对象上 scope（缩小面积）；② Text2SQL 第 9 道防线**先于** scope 功能上线；③ 建 ≥20 条安全测试用例做回归门禁 |
| **R4** | **Agent 以 system 身份绕过治理** | 治理层对最活跃写入方失效，等于没做 | ① `actor_type` 必填；② `PermissionRegistry` 加断言：Agent 身份不得持有任何 `*.approve` 权限；③ 审计日志必须记录 Agent 的 `run_id` 与 `scene_key` |
| **R5** | **"受控"被业务方视为负担**（改个字也要走流程） | 用户绕过系统，在共享盘维护"影子文件" | ① 提供**有期限的临时偏离（deviation）**：可先用后补批，到期自动生成补批任务；② minor 修订走"单人审阅"而非全会签；③ 试点期只对 3 类文件强制受控（SOP / 检验标准 / 图纸），其余建议受控 |
| **R6** | **SQLite 单写者限制**：`WorkflowEngine` 直连 sqlite3，并发会签会锁库 | 多部门同时签会报 `database is locked`；本轮用**进程内 `threading.RLock` 串行化治理写路径**，因此**多实例部署（多 worker / 多容器）时会失效**——锁只在单进程内有效 | ① 本轮已用 `RLock` + `governance_json` 单写者串行化，单进程下并发测试通过（`test_concurrent_cosign_records_exactly_one`）；② **生产化必做（M1.7）**：换 `wf_signoff` 独立表 + `(task_uid, role_key, actor, verb)` 唯一索引，把"唯一性"从进程锁下沉到数据库约束；③ 连接改 WAL + `busy_timeout`；④ 生产环境切 MySQL（已支持，见 `docker-compose.yml`）。README「生产化清单」已记录 |
| **R7** | **PDF 导出能力缺失**（Huly 有独立的 `print` 服务，我们零） | S6/S8 的"受控文件发放"无法交付 | **裁定 3 已定选型**：前端 `@media print` + 服务端 Playwright `page.pdf()`，同一份 CSS。**不用 WeasyPrint**（依赖系统 cairo/pango，Windows Server 部署痛；Playwright 已在项目依赖内）。模板与文档字段一起设计，不后补 |
| **R8** | **中文全文检索召回率不达标**（FTS5 默认分词对中文无效） | S9 的案例召回形同虚设 | 阶段二 M2.2 前先做 30 条真实查询的召回测试；FTS5 用 trigram tokenizer 或 jieba 预分词二选一，**以测试结果定，不预先拍板** |
| **R9** | **数据迁移风险**：给现有表加 `scope_type/scope_id` 与 `actor_type` 列 | 历史数据 scope 为空 → 查询变空集 → 现场以为数据丢了 | 迁移脚本必须给历史数据填**默认 scope = `dept:legacy`**（全员可见），并出迁移报告（各表多少行被填默认值）；迁移前全库备份 |
| **R10** | **阶段二客诉数据未做客户级隔离**（裁定 5 明确要求列入风险清单） | 客诉数据在阶段二**仅靠角色级脱敏兜底**（`text2sql/masker.py` 的字段脱敏 + 角色可见性），**未做 `customer` 维度数据隔离**。若 A 客户与 B 客户的客诉同在"质量部可见"范围内，具备质量角色的用户可跨客户查看 → 极可能被客户合规审计或 NDA 挑战 | ① **交付说明与验收报告中显式声明此已知缺陷**，不得沉默；② 阶段二上线前与客户确认"客诉数据是否允许跨客户可见"；③ 若客户要求立即隔离，则 `customer` scope 提前到阶段二（工期 +1 周）；④ 阶段三必须补齐 `customer` + `project` scope，并在补齐前不对外承诺"客户级隔离" |
| **R11** | **小厂兼岗与"一人一签"的冲突**（裁定 G6 的必然副作用） | 现实中 SQE 可能同时兼 PQE、质量经理可能同时兼 QA。落实一人一签后，这些岗位**无法凑齐会签人数**，工单会卡在 `waiting_hitl`；一旦系统提供"自签多角"的便利通道来规避，G6 立即失效，治理层形同虚设 | ① **制度上要求职责分离（SoD）**——这本身就是 ISO 9001 / IATF 16949 的合规要求，不是我们额外加的门槛；② 系统**不提供"一键自签多角"的便利通道**，只提供「换人签署」（把该会签位指派给具备同权限的另一人）与既有的「代签 + 留痕」（裁定 4，需 gm/quality_director + 理由 + `on_behalf_of`）；③ 若客户确实无法分离职责，需在**交付文档中显式记录该组织的 SoD 例外**，由客户方**书面确认**——把合规责任落在组织决策上，而不是让系统悄悄放宽 |

## 6. 不做清单

| # | 不做 | 理由 |

| N1 | **不做通用低代码/无代码平台**（不做拖拽式表单、不做可视化流程设计器） | Huly 用 60+ 模型包 + 90+ 插件包做到了，代价是 30 个微服务（`ARCHITECTURE_OVERVIEW.md:5`），且最终仓库冻结、托管版关停（`README.md:8-21`）。我们的场景 YAML 已经是"面向我们业务的低代码"，**再抽象一层只会让业务方更难懂**。场景由我们（产品+工程）改 YAML，不让客户自己拖拽 |
| N2 | **不做完整 IM**（不做群管理、消息漫游、表情、已读回执、音视频） | 企业微信已经做了，且用户已经在里面。我们只做**卡片 + 双向会签 + 通知**，依附而不是对抗。自建 IM 是典型的"功能看起来很大、价值密度很低" |

| N4 | **不引入 CockroachDB / Redpanda / Elasticsearch / Kafka** | 见对标分析 §5 第 2、3、4 项。这些是"多租户 SaaS 横向扩展"的解，我们是"单厂纵向深度"，用 SQLite-PostgreSQL + 进程内事件总线 + FTS5 已足够。**运维复杂度是 3 人团队的硬约束** |
| N5 | **不上 CRDT（Y.js）实时共编** | 见对标分析 §5 第 6 项。我们的冲突是"写哪一段"不是"同一字符同时改"。改用段落认领 + 批注，成本低一个数量级 |

| N8 | **不做电子签章的 CA 对接**（不接第三方 CA / 不做证书签名） | Huly 有 `sign` 服务用 `P12Signer` 签 PDF（`services/sign/pod-sign/src/sign.ts:1-40`），但那需要证书生命周期管理（申请/续期/吊销/HSM）。我们阶段一只做**"系统内签名 + PDF 水印 + 审计留痕"**，法律效力由客户现有纸质签批流程兜底。真需要 CA 时再单独评估 |

| N10 | **不做 BI/看板可视化引擎** | 我们已有 `v2/data/metrics/*.yaml`（complaint/iqc/otd）声明式指标。V3 只扩充指标，不做拖拽式图表配置 |

## 6.5 不采纳但记录（可逆决策，附"再考虑条件"）

> 与 §6「不做清单」的区别：§6 是**产品方向性的划掉**（不打算做）；本节是**技术上确认其价值、但当前不采用的机制**——属于可逆决策，条件变化即可重启评估。记录的目的是**避免下一轮重新论证**。

| # | Huly 的机制 | 它的价值 | 为什么不采纳（当前） | 什么条件下再考虑 |
|---|---|---|---|---|
| K1 | **`Permission.forbid`（负权限）** | 黑名单优先于白名单，用于"整体授权但排除个别人"（如"质量部全可见，但实习生不可见成本字段"）。实现见 `foundations/server/packages/middleware/src/spacePermissions.ts:194,198`（`permission.forbid !== undefined ? !permission.forbid : true`） | 负权限的**推理复杂度是正权限的超线性倍**：多角色叠加后"谁被 forbid 了"很难人工验证，极易出现"本意排除却实际放行"。我们目前 15 个角色、21 条权限的规模，用正权限 + 显式拒绝（fail-closed）已能表达全部需求 | ① 出现"同一角色内必须排除个别人"的真实诉求 ≥3 次；② 且无法通过拆分角色解决。届时先做**只读的 forbid 校验器**（能算出某人对某对象是否被 forbid），再考虑写入侧 |
| K2 | **`Permission.txClass` / `objectClass` / `txMatch`（事务级授权）** | 权限可精确到"允许对某类对象执行某类事务，且事务内容需匹配查询条件"。见 `foundations/core/packages/core/src/classes.ts:570-579`、`spacePermissions.ts:177-193` | 它解决的是"**通用平台**要允许第三方定义任意权限"的问题。我们的权限是**动作型**（`hitl.<slot>.<verb>`，21 条全是"发起/会签/终批"），没有"对某字段执行某事务"的需求。引入后每次校验都要跑 `matchQuery`，且我们的场景 YAML 已经是更上层的声明 | ① 出现"字段级授权"硬需求（如"成本相关字段仅财务与 GM 可改，其余角色只读"）；② 或受控文档需要"仅编制人可改正文、仅批准人可改状态"。届时**先只加 `objectClass`**，暂不加 `txMatch` |
| K3 | **30+ 微服务拆分**（`ARCHITECTURE_OVERVIEW.md:5`） | 独立扩容、独立部署、故障隔离；`collaborator` 可独立扩、`fulltext` 可独立重建 | ① 微服务的收益以**有 SRE** 为前提，3 人团队下 30 份配置/日志/健康检查会把故障率推高而可用性推低；② 我们的 QPS 与数据量用单进程 + 1 个 DB 完全够；③ Huly 自己用 30 微服务换来的通用性，最终仓库冻结（`README.md:8-21`）——**通用性没有换来可持续的商业** | ① 文档解析（`doc_parser`）或 PDF 渲染（Playwright）成为 CPU 瓶颈，需独立扩缩；② 或出现"某个能力必须独立部署在客户内网"的要求。届时**只拆 1-2 个无状态 worker**，不动主链路 |
| K4 | **CRDT（Y.js）实时共编**（`ARCHITECTURE_OVERVIEW.md:35`） | 真正的多人同屏编辑，字符级冲突自动合并，支持离线 | ① 我们的冲突类型是"**谁负责写哪一段**"（8D 的 D1-D8、受控文档的章节），不是"同一字符被两人同时改"；② CRDT 需要长连接 + 状态同步 + 离线合并 + 冲突可视化完整栈，成本高一个数量级；③ 制造业评审的现实是"各写各的段、会上过一遍"，不是 Google Docs 式同屏 | ① 出现"多人必须同时编辑同一段且不能互相覆盖"的真实场景 ≥2 个；② 或客户明确要求"像在线文档一样"。届时优先评估**轻量方案**（段落锁 + 乐观并发 + 自动合并提示），CRDT 作为最后手段 |
| K5 | **`pods/embeddings` 向量化服务**（Python，标准库 `http.server` + HuggingFace `AutoModel` + Mean Pooling） | 自托管 embedding，不依赖外部 API；三个端点 `/embeddings` `/completion` `/compare`（`pods/embeddings/server.py:22-32`） | **它自己就是 demo**：`pods/embeddings/readme.md` 明确写 "Enable Embeddings **demo server** for workspace"，通过 `--embeddings true` 标志打开；实现是 `BaseHTTPRequestHandler` 单文件，无并发、无队列、无鉴权。我们已有的 ChromaDB + `contracts/vector_store.py` 契约层在能力上已覆盖，并支持切换 embedding 后端 | ① 出现"客户内网无法调用任何外部 embedding API"的硬约束；② 且本地 embedding 质量满足召回要求。届时**用 FastAPI + batching 重写**（不照抄单文件 demo），并保留 `vector_store.py` 契约不变 |
| K6 | **组织层级（`reports_to` / 汇报关系）** 用于"代签必须是直接上级"的严格校验 | 代签授权可精确到"只能代自己的直接下属"，审计链更严 | **组织层级是组织数据，不是权限模型常量。** 理由三层：① 每个工厂的汇报关系不同（有的厂质量总监直管 SQE，有的厂 SQE 归采购管），硬编码进 `permissions.yaml` 等于把**一家工厂的组织结构焊死在平台里**——这正是我们从 Huly 学到教训的反面（它的 Role 挂在 SpaceType 上而非硬编码组织树，`models/core/src/security.ts:139-162`）；② "任何 gm/quality_director 可代任何角色的签"在合规上**不是漏洞而是授权边界**——ISO 审核问的是"谁有权代签 + 有没有理由 + 能不能追溯"，不是"是否严格直接上级"；③ 会引出"菱形汇报/兼岗/代理期"等一堆边界，不是两行 YAML 能收口 | **组织架构数据可得时**——即接入企业微信 / 钉钉组织架构或客户 HR 系统之后。届时用**外部组织数据**做层级校验，**而不是写进配置文件**。在此之前，用裁定 4 的 C1-C4 四条兜底（强制理由 + `overdue_signoff` + 仅 gm/quality_director + `on_behalf_of` 必填） |
